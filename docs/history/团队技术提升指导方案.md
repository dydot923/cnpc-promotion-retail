### 1.3 核心优势（值得团队学习的优秀实践）

#### 优势 1：规则引擎策略模式架构

项目最核心的亮点是 `ruleengine` 模块的设计。通过 `BenefitCalculator` 接口 + 策略模式，实现了促销类型的可扩展性：

```
ruleengine/
  benefit/         → 12 个独立计算器（FixedPrice, AmountOff, PercentageDiscount, ExchangePurchase, GiftItem, GiftCoupon, BundlePrice, CouponRedeem, FuelVolumeDiscount, Composite...）
  condition/       → 条件匹配器（Date, Member, Province, StationType, TimeRange）
  conflict/        → 互斥与叠加冲突解决器
  ranking/         → 候选方案排序器
  explanation/     → 可解释文本生成器
  context/         → 订单上下文（Cart, Fuel, Customer, Station）
  model/           → 领域模型（PromotionRule, PromotionCandidate, BlockedPromotion, CalculationResult）
```

**学习要点**：新增促销类型只需新增一个 Calculator 实现类，不修改现有代码（开闭原则）。

#### 优势 2：BigDecimal 全量合规

工程约束文档明确禁止 `double`/`float`，实际代码扫描确认 **零违规**。所有金额比较使用 `compareTo`，舍入使用 `setScale(2, RoundingMode.HALF_UP)`。

#### 优势 3：前端边界守护

前端冒烟测试中有 `forbiddenFrontendPatterns` 正则数组，自动扫描前端源码是否包含促销计算逻辑。这是一种非常好的"架构守护测试"实践。

#### 优势 4：双持久化策略

每个 Repository 接口都有 `InMemory` 和 `Mybatis` 两套实现：
- 开发环境用内存版，不依赖数据库，`mvn test` 秒级启动
- 生产环境用 MyBatis Plus + Flyway，数据库迁移可追溯

#### 优势 5：原价兜底机制

`PromotionEngine.calculate()` 始终返回 `originalPriceFallback`，确保即使所有规则都不可用，收银员也能以原价结算。这是金融级系统的防御性设计。

## 二、发现的问题与改进建议

### 2.1 P0 — 必须立即修复

#### 问题 1：根目录存在垃圾文件 `nul`)`

项目根目录有一个名为 `nul`)\`` 的文件（475 字节），明显是 Windows 下输出重定向 `> nul` 时误操作产生的。

**修复建议**：删除该文件，并在 `.gitignore` 中添加 `nul*` 规则。

#### 问题 2：数据库凭据硬编码

`docker-compose.yml` 和 `start-all.bat` 中明文写了 `cnpc/cnpc` 数据库密码。虽然当前是开发环境，但这违反了安全最佳实践。

**修复建议**：
- 使用 `.env` 文件管理环境变量（已在 `.gitignore` 中排除）
- `docker-compose.yml` 使用 `${DB_PASSWORD}` 变量引用
- 提供 `.env.example` 模板

#### 问题 3：`auth` 模块为空壳

`auth` 模块只有 `package-info.java`，没有任何实现。所有 API 端点无认证保护。

**修复建议**：至少添加 Spring Security 基础配置，实现 JWT 或 Session 认证。

### 2.2 P1 — 应在 2 周内修复

#### 问题 4：无 CI/CD 流水线

项目没有任何自动化构建/测试流水线。所有测试依赖开发者本地手动执行。

**影响**：
- 代码合并到主分支前无法自动验证
- 无法保证构建一致性
- 回归问题无法及时发现

**修复建议**：创建 GitHub Actions / GitLab CI 配置：
```yaml
# .github/workflows/ci.yml 示例框架
name: CI
on: [push, pull_request]
jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }
      - run: cd backend && mvn -B test
  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: cd frontend && npm ci && npm run build && npm test
```

#### 问题 5：无代码静态分析工具

| 语言 | 缺失工具 | 建议引入 |
|---|---|---|
| Java | Checkstyle, SpotBugs, PMD | Maven 插件集成 |
| TypeScript | ESLint, Prettier | npm devDependencies |

**修复建议**：

前端 ESLint + Prettier 配置：

#### 问题 7：前端测试覆盖极低

当前前端只有 1 个冒烟测试脚本（静态文件扫描），没有任何组件测试或单元测试。

**修复建议**：引入 Vitest + React Testing Library：
```bash
npm install -D vitest @testing-library/react @testing-library/jest-dom jsdom
```

#### 问题 8：前端硬编码值

`CheckoutPage.tsx` 中硬编码了 `"规则版本 V22"` 和 `"247 条 CONFIRMED"`，这些应该来自后端动态数据。

### 2.3 P2 — 持续改进项

#### 问题 9：API 文档未默认开启

`springdoc-openapi` 放在 `integration-deps` profile 中，默认不启用。建议默认开启，或至少在 dev profile 中开启。

#### 问题 10：无前端 Docker 化

`docker-compose.yml` 只包含 PostgreSQL，前端没有容器化。建议添加前端 Dockerfile 和 docker-compose 服务。

#### 问题 11：单一 CSS 文件

所有样式集中在 `styles.css` 中，随着项目增长会难以维护。建议使用 CSS Modules 或 Tailwind CSS。

#### 问题 12：无前端 Error Boundary

当前只有 `Suspense` 加载态，缺少 `ErrorBoundary` 组件级错误捕获。

#### 问题 13：无环境变量模板

`.gitignore` 排除了 `.env`，但没有提供 `.env.example` 模板文件。

### 4.3 通用工程能力

#### Git 协作规范

```
分支命名：
  feature/PRO-123-add-coupon-redeem     ← 新功能
  fix/PRO-456-fix-bigdecimal-rounding   ← Bug修复
  refactor/PRO-789-extract-benefit-base ← 重构
  hotfix/PRO-999-crash-on-empty-cart    ← 紧急修复

提交信息格式：
  type(scope): subject

  type:   feat | fix | refactor | test | docs | chore | perf
  scope:  ruleengine | checkout | frontend | import | inventory | ...
  subject: 简洁描述（不超过50字）

示例：
  feat(ruleengine): 新增券核销计算器 CouponRedeemBenefitCalculator
  fix(checkout): 修复空购物车时 NPE
  test(frontend): 添加 CheckoutPage 组件测试
```

#### Code Review 心态

1. **对事不对人** — Review 代码，不 Review 人
2. **提供方案** — 不仅指出问题，还给出建议
3. **区分优先级** — P0 必须改，P2 可以后续迭代
4. **肯定优秀实践** — 看到好代码要表扬
5. **控制 Review 粒度** — 单次 Review 不超过 400 行

#### 方法长度与复杂度

- 单个方法 **不超过 50 行**
- 圈复杂度 **不超过 10**
- 嵌套层级 **不超过 3 层**
- 参数个数 **不超过 5 个**（超过用对象封装）

#### 异常处理层级

```
  └→ 抛出领域异常（如 CheckoutCalculationNotFoundException）

Repository 层
  └→ 只抛出数据访问异常，不吞异常
```
