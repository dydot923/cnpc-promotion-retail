## 2. 严重问题清单

### P0-1 一键启动在干净环境下可能无法启动 PostgreSQL

证据：

- `docker-compose.yml` 要求 `POSTGRES_PASSWORD` 必须来自环境变量或 `.env`。
- 仓库只有 `.env.example`，没有 `.env`。
- `start-all.bat` 设置了 `DB_PASSWORD=cnpc`，但没有设置 `POSTGRES_PASSWORD`。
- 实测未设置 `POSTGRES_PASSWORD` 时，`docker compose config` 报错：`required variable POSTGRES_PASSWORD is missing a value`。

影响：

- 与 02 号落地文档中的“双击 start-all.bat 一键启动”冲突。
- 收银电脑或新开发环境首次启动时，PostgreSQL 容器无法创建，后端 `dev-db` 随后无法连接数据库。

整改建议：

1. 在 `start-all.bat` 中同时设置 `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_PORT`，并传给 `docker compose`。
2. 或将 `docker-compose.yml` 的本地开发默认值改为 `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-cnpc}`，生产环境再用部署环境覆盖。
3. 更新 README，明确 `.env` 不是一键启动的前置条件。

验收：

- 删除或忽略本地 `.env`，清空 `POSTGRES_PASSWORD` 环境变量后，`docker compose -f .\docker-compose.yml config` 通过。
- `NO_PAUSE=1 NO_OPEN=1 start-all.bat` 可以完成数据库、后端、前端的启动检查。

### P0-2 文档规划的数据库新增表与实际 V1-V22 表结构已经分叉

证据：

- 21/22 号文档规划 V23-V30 新增 `member`、`member_level`、`coupon_template`、`coupon_instance`、`product_group`、`bundle`、`transaction`、`transaction_item`、`inventory_alert`。
- 实际迁移 V4 已创建 `coupon_template` 和 `coupon`，字段使用 `coupon_template_id`、`coupon_id`、`face_value`、`min_spend_amount`。
- 实际迁移 V5 已创建 `product_group`、`product_group_item`、`bundle`、`bundle_item`，且主键和字段名与文档规划不同。
- 实际迁移 V1-V22 尚未创建 `member`、`member_level`、`transaction`、`transaction_item`、`inventory_alert`。

影响：

- 如果直接按文档新增 V23-V30，容易产生重复表或同名表字段冲突。
- 券、组合包、商品组会出现“文档模型”和“代码模型”两套口径，后续维护成本高。

整改建议：

1. 先冻结一份“当前数据库基线说明”，以 V1-V22 和现有 MyBatis Entity 为准。
2. 数据库新增采用“演进现有表”优先，不重复创建已存在能力：
   - `coupon` 作为当前券实例表继续演进。
   - `coupon_template` 继续沿用当前字段命名，必要时增补兼容字段。
   - `bundle`、`product_group` 继续沿用当前主键和字段命名。
3. 对文档规划表做映射表，明确哪些是新增、哪些是已实现但命名不同、哪些要补字段。

验收：

- 新增一份数据库基线文档或 ADR。
- Flyway 新迁移只从 V23 往后追加，不改写 V1-V22。
- `FlywayMigrationTest` 或 Testcontainers 集成测试覆盖 V1-V23+ 全量迁移。

### P0-3 会员券链路还不是服务端可信闭环

证据：

- 当前没有 `member`、`member_level` 表，也没有 `member` 模块服务。
- 前端收银页会把 `availableCoupons` 作为请求体传给 `/api/checkout/calculate`。
- 后端券核销可将选中券置为 `USED`，但缺少“按会员从数据库查询可用券”的服务端链路。
- `coupon` 表已有 `holder_member_id`，但 `Coupon` 领域模型和 `CouponEntity` 未映射该字段。

影响：

- 会员专属券、会员等级、会员生日月、可用券列表仍主要依赖前端输入或演示数据。
- 后续做“会员新增”和“券新增”时，如果不先统一会员编号和券归属，会出现核销、发放、查询三条链路互不一致。

整改建议：

1. 新增 `member`、`member_level` 表和对应仓储、服务、接口。
2. 将 `holder_member_id` 纳入券领域模型和 MyBatis Entity。
3. Checkout 计算时由后端根据 `memberCode`、`selectedCouponIds` 查询可用券，不再信任前端提交完整券对象。
4. 增加 `CouponRepository.findAvailableByMemberId(...)` 或等价查询。

验收：

- 通过 `POST /api/members/identify` 识别会员。
- 通过会员编号查询可用券。
- 收银请求只传会员和券 ID，后端自行加载券详情并校验状态、归属、有效期、适用范围。
- 券核销后再次计算不可重复使用。

### P1-1 结算确认没有形成完整交易流水

证据：

- 当前确认结算落在 `checkout_confirmation`，保存候选快照。
- 文档要求交易记录和交易明细表，用于交易追踪、报表、券发放、积分和库存扣减。
- 实际没有 `transaction` / `transaction_item` 表，也没有交易明细仓储。

影响：

- 可以证明“选择了哪个促销方案”，但不能完整支撑交易日报、促销效果分析、积分累计、库存扣减。
- 后续新增报表或会员积分时缺少事实表。

整改建议：

1. 新增交易流水表，建议避免直接使用 `transaction` 作为表名，可命名为 `checkout_transaction` 和 `checkout_transaction_item`。
2. 确认结算时在同一事务内写入确认记录、交易头、交易明细、券核销、后续赠券发放记录。
3. 为交易号、会员、站点、时间建立索引。

验收：

- 确认结算后可按交易号查询交易头和明细。
- 交易金额与候选快照一致。
- 重复确认仍被拦截。

### P1-2 库存预警当前偏计算型，缺少可处理状态持久化

证据：

- 文档规划 `inventory_alert` 表，包含 `status`、`handled_at`。
- 当前 V1-V22 未创建 `inventory_alert` 表。
- 当前库存预警页面和服务主要从库存、规则、组合包现算预警。

影响：

- 可以展示预警和生成补货清单，但不适合做“已处理/待处理/历史追踪”。
- 站长处理预警后缺少闭环记录。

整改建议：

1. 先确认库存预警是否需要持久化处理状态。
2. 如需要，新增 `inventory_alert` 或 `inventory_alert_event` 表，避免与现算预警重复。
3. 保留现算能力作为实时预警来源，持久表只记录处理状态、确认人、处理时间和备注。

验收：

- 预警可标记处理。
- 刷新后处理状态仍保留。
- 补货清单能关联处理记录。

## 3. 数据库新增推荐顺序

1. 修复一键启动 PostgreSQL 环境变量问题。
2. 输出数据库基线 ADR：确认沿用当前 `coupon` / `coupon_template` / `bundle` / `product_group` 结构。
3. V23 新增 `member_level`、`member`。
4. 演进 `coupon`，补齐 `holder_member_id` 领域映射、会员券查询索引和服务端查询接口。
5. 新增 `checkout_transaction`、`checkout_transaction_item`。
6. 根据产品确认，新增库存预警处理状态表。
7. 前端再接入会员识别、会员券查询、交易查询页面。
