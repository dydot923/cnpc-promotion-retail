## 一、数据完整性约束

### 1.1 不修改原始 Excel
- `data/` 下原始 Excel 的单元格内容不可修改
- 补充演示数据通过 Flyway/SQL 脚本或测试数据初始化
- **SQL 补充的演示数据必须打 `is_demo_data = true` 标记**
- 演示数据不参与生产导入流程
- 三个月后必须能区分真实业务数据与演示补位

### 1.2 金额精度
- 所有金额使用 `BigDecimal`
- 金额比较使用 `compareTo`，禁止 `==` / `>`
- 舍入显式指定 `setScale(2, RoundingMode.HALF_UP)`
- 商品编码和条码按 `String` 处理

### 1.3 数据库迁移安全
- Flyway 迁移脚本必须幂等
- 不得破坏已有数据
- 涉及新增非空字段时，提供 DEFAULT 值或分步迁移（先加列 → 回填数据 → 加约束）
- 所有批量数据导入操作必须记录对应的 Flyway 版本号
- 支持按版本回滚

## 二、架构边界约束

### 2.1 前端边界
- **禁止**：促销规则可用性判断、最终应付金额计算、优惠叠加判断、活动日期/门槛判断、库存是否足够判断、品类排除（香烟/化肥）
- **允许**：输入校验（购物车非空、条码格式合法）、结果展示、加载状态、错误提示
- 前端 mock 数据必须从后端 API 响应模板生成
- 后端 API 契约变更时同步更新 mock 模板
- 建议增加独立 contract test 验证前后端契约一致性

### 2.2 后端模块边界
```
ruleengine    促销计算唯一入口
checkout      只调用 ruleengine，不自行判断
promotion     规则管理，不负责计算
importcenter  导入和清洗，不生成结算结果
inventory     库存查询和阈值，不决定促销价格
audit         操作日志，不参与计算
```

### 2.3 异常处理
- 不可用规则必须进 `BlockedPromotion` 并附带具体原因
- Excel 异常行必须进入异常报告，不得跳过
- 不得静默丢弃任何异常

### 2.4 数据结构独立性
- `product_group` 映射必须是独立表结构（`product_group` + `product_group_item`）
- 不得硬编码在规则参数中
- 新增映射只加数据不改代码

## 三、规则生命周期约束

### 3.1 版本与状态
- 版本号标识"这批规则从哪个版本的源数据导入"（如 `activity-board-v2`）
- **版本号不替代状态管理，不作为 checkout 加载过滤条件**
- checkout 加载规则以 `status = CONFIRMED` 为唯一过滤条件
- 规则生命周期：`DRAFT → CONFIRMED → DEPRECATED → ARCHIVED`

### 3.2 规则冲突与优先级
当一个商品同时命中多条规则时：
1. 按 `exclusiveGroup` 互斥组分组 — 同组内只取优先级最高的候选
2. 不同 `exclusiveGroup` 且 `stackable = true` 的规则可叠加
3. `priority` 数值越小优先级越高
4. **9.9 专区（`fixed_price`）和全场折扣（`discount`）默认互斥**，不得同时作用于同一商品
5. 冲突处理逻辑必须有测试覆盖（至少 2 个互斥场景 + 1 个叠加场景）

### 3.3 规则可追溯
每条规则必须有：`ruleId`、`activityId`、`ruleType`、`priority`、`exclusiveGroup`、`stackable`、`status`、`version`、`createdAt`、`updatedAt`、`createdBy`、`updatedBy`

## 四、质量与测试约束

### 4.1 测试覆盖率
- 新增规则类型的测试覆盖率不低于 80%
- 简单规则（如 `fixed_price`）：至少 3 个测试用例（正常命中 / 条件不满足 / 边界值）
- 复杂规则（如 `exchange_purchase`、`coupon_redeem`）：至少 5 个测试用例，覆盖：
  - 正常命中
  - 条件不满足
  - 边界值
  - 互斥场景
  - 库存/券状态异常
- 每个测试用例必须验证解释文本输出

### 4.2 测试环境
- 不强行启动长驻服务 — 前端测试用 mock 或 skip 策略
- Docker/Testcontainers 不可用时，相关测试 skip 而非 fail
- `mvn test` 标准：0 failures, 0 errors（skipped 仅限 Docker 不可用）
- `npm test` 标准：通过或合理 skip
- `npm run build` 标准：通过（Vite chunk warning 可接受）

## 五、性能约束

### 5.1 结算响应时间
- 单次 `PromotionEngine.calculate()` 响应时间不超过 2 秒
- 规则匹配量 n=50 商品 × m=500 规则时，必须在 1 秒内完成
- 如果发现性能问题，优先优化规则索引（按 `ruleType` + `productScope` 预筛选）
- 不得通过降低匹配精度来提升性能

## 六、变更检查清单

```
- [ ] 0 double/float/Double/Float

- [ ] data/ 原始 Excel 未修改
- [ ] 所有新规则有版本号
- [ ] 不可用规则有原因
- [ ] 原价兜底始终存在
- [ ] 演示数据有 is_demo_data = true 标记
- [ ] Flyway 迁移幂等且不破坏已有数据
- [ ] 规则冲突有 exclusiveGroup/priority/stackable 定义
- [ ] 新增规则测试覆盖率 ≥80%
- [ ] 单次 calculate 50商品×500规则 < 1秒
- [ ] 前端 mock 模板与后端 API 契约一致
```

## 七、与原始工程约束的关系

本文档是《Codex 工程约束：防止屎山代码》（v1）的**补充和修订**，不替代 v1 中的以下内容：
- 第二章 架构边界约束（模块结构、禁止行为）
- 第三章 促销规则引擎约束（引擎职责、内部结构、规则类型扩展方式）
- 第四章 金额与数量约束（BigDecimal、舍入、编码条码）
- 第五章 Controller 与 Service 约束
- 第六章 前端约束
- 第七章 Excel 导入约束
- 第八章 规则版本与审计约束
- 第九章 测试约束
- 第十章 命名与代码风格约束
- 第十一章 AI 海报模块约束
- 第十二章 Codex 生成代码前检查清单
- 第十三章 Reviewer 拦截标准

v2 对 v1 的**修订点**：
1. 前端约束：从"不写业务判断"收紧为"不写促销规则判断和金额计算"（允许输入校验）
2. 规则版本：从"必须有版本"细化为"版本号仅标识导入批次，不替代状态管理"
3. 测试标准：从"正反例各1个"提高到"覆盖率≥80%，简单≥3用例，复杂≥5用例"
4. 演示数据：新增 `is_demo_data` 标记要求
5. 前端测试：新增 mock 模板与 API 契约同步要求

v2 对 v1 的**补充点**：
1. 数据库迁移安全约束（幂等、不破坏数据、可回滚）
2. 规则冲突与优先级约束（exclusiveGroup/priority/stackable）
3. 性能约束（单次结算响应时间）
4. Contract test 建议（前后端契约一致性）
