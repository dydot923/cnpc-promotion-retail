# 项目目的、逻辑搭建与调用方法说明

## 1. 项目目的

本项目是面向加油站便利店场景的智能零售促销系统，重点解决以下问题：

1. **促销判断依赖人工**：将固定价、折扣、满减、买赠、赠券、换购、组合包等活动规则转为可计算的结构化规则，避免收银员在高峰期人工查表。
2. **油非联动规则复杂**：根据商品、数量、会员、油品类型与金额、站点、日期、时间等订单上下文，计算可执行的优惠方案。
3. **促销与库存脱节**：在促销计算、库存预警和补货清单之间建立关联，识别低库存、缺货和组合包缺件风险。
4. **规则变更不可追溯**：通过导入批次、规则草稿、确认版本、停用和审计日志，保留活动规则的治理链路。
5. **门店营销物料准备慢**：前端提供活动选择、提示词拼装、海报预览与审核流程；当前为演示流程，尚未调用外部 AI 图像模型。

项目定位为可与 POS、会员、电子券、库存等现有系统逐步集成的促销决策与运营辅助平台，不替代现有支付和收银主系统。

## 2. 项目结构与职责

```text
frontend/                         React 18 + TypeScript + Vite
  src/pages/                      收银、运营看板、导入、库存、规则等页面
  src/api/                        后端接口调用封装
  src/components/                 布局、错误边界、价格等通用组件

backend/                          Java 21 + Spring Boot 3
  ruleengine/                     条件匹配、权益计算、冲突处理、排序、解释
  checkout/                       计算记录、用户确认、交易、积分与券处理
  promotion/                      规则草稿、版本、券、积分、权益包等治理能力
  importcenter/                   Excel 导入、批次与异常行处理
  product/                        商品查询与商品目录
  inventory/                      库存快照、预警与补货关联
  replenishment/                  补货清单创建、查询与导出
  station/                        站点查询与站点上下文
  audit/                          跨模块操作审计
  common/                         API 返回体、配置、持久化装配、业务日期

data/                             价格、库存、活动看板等原始业务数据
docs/                             需求、设计、测试、导入和治理文档
```

### 2.1 前后端边界

前端只负责录入、调用、展示和用户确认，不计算优惠金额、不判断促销可用性。促销匹配、金额计算、规则互斥、库存约束和审计均在后端完成。

前端公共入口是 `frontend/src/api/request.ts` 中的 `apiRequest<T>()`：

- 使用浏览器 `fetch()` 发起请求；
- 使用 `AbortController` 和 `VITE_API_TIMEOUT` 实现超时取消；
- 自动拼接 `VITE_API_BASE_URL`（默认 `/api`）；
- 自动设置 JSON 请求头，上传 `FormData` 时不手动设置 `Content-Type`；
- 解包统一的 `ApiResponse<T>`，将网络、超时和业务错误转换为 `ApiRequestError`。

## 3. 核心业务逻辑

### 3.1 数据导入与规则治理

```text
价格 / 库存 / 活动看板 Excel
        ↓
导入接口与格式校验
        ↓
导入批次、异常行记录
        ↓
商品、库存、促销规则等结构化数据
        ↓
规则草稿确认、生成规则版本、审计记录
        ↓
仅 CONFIRMED 状态规则参与促销计算
```

导入模块负责文件解析、字段校验、批次记录与错误导出。规则治理模块负责草稿确认、拒绝、停用、版本查询和审计，防止未确认或已停用的规则直接进入收银计算。

### 3.2 收银促销计算

```text
收银员录入商品 / 油品 / 会员 / 站点信息
        ↓
POST /api/checkout/calculate
        ↓
CheckoutApplicationService.calculate()
        ↓
构建 OrderContext，读取已确认规则
        ↓
DefaultPromotionEngine.calculate()
  条件匹配 → 权益计算 → 互斥处理 → 候选排序 → 解释生成
        ↓
返回推荐方案、可用方案、不可用原因、规则版本和原价兜底
```

`OrderContext` 由购物车、顾客、油品和站点四类上下文组成。规则计算始终生成原价候选方案，因此当没有可用促销、规则未确认或计算器未覆盖某种规则时，系统仍能返回原价结算结果。

### 3.3 结算确认与交易闭环

```text
用户选择候选方案或跳过促销
        ↓
POST /api/checkout/confirm
        ↓
读取 calculationId 对应的计算快照
        ↓
校验未重复确认、未重复订单、候选方案存在
        ↓
核销已使用券 → 发放赠券 → 保存确认记录与交易
        ↓
计算并发放会员积分 → 写入审计日志
```

确认流程使用事务控制。`CheckoutApplicationService.confirm()` 会避免同一计算结果被重复确认，并把用户最终选择、交易明细、券处理和积分变动留在可查询记录中。

### 3.4 库存预警与补货

库存模块以商品编码关联库存快照和活动商品。低于安全阈值时生成预警记录；补货模块根据预警创建清单并导出。前端不自行计算库存状态，而是调用库存、预警和补货接口展示后端结果。

### 3.5 AI 海报演示流程

`frontend/src/api/poster.ts` 中的 `buildPosterPrompt()` 根据活动和商品生成受控提示词，`createPosterTask()` 创建待确认的演示任务。`PosterPage` 展示预览和确认发布状态。

当前该模块未调用外部图像生成 API，页面已有“AI 服务未配置”的提示。后续接入模型时，应由后端保管密钥，并将商品名称、价格和活动条件继续从结构化规则数据中生成，避免模型自由生成关键营销文案。

## 4. 后端核心方法

| 模块 | 核心方法 | 作用 |
| --- | --- | --- |
| 促销引擎 | `DefaultPromotionEngine.calculate(context, rules)` | 遍历有效规则，汇总可用候选与阻断原因，返回推荐方案及原价兜底。 |
| 条件匹配 | `ConditionMatcher.match(context, rule)` | 判断规则状态、日期、时间、站点、会员、油品、金额、商品和数量等条件。 |
| 权益计算 | `BenefitCalculator.calculate(context, rule, totals)` | 按规则类型计算优惠候选或返回不可用原因。 |
| 冲突处理 | `ConflictResolver.resolve(candidates)` | 处理互斥组与不可叠加关系，保留可执行候选。 |
| 推荐排序 | `CandidateRanker.recommend(candidates)` | 从候选方案中选择推荐方案。 |
| 解释生成 | `ExplanationBuilder.summarize(...)` | 生成促销命中和阻断原因的可读说明。 |
| 收银计算 | `CheckoutApplicationService.calculate(request)` | 构建订单上下文、调用规则引擎、保存计算快照、返回积分预览。 |
| 收银确认 | `CheckoutApplicationService.confirm(request)` | 校验候选，完成券处理、交易保存、积分发放与审计。 |
| 换购查询 | `CheckoutExchangeOfferService.findOffers(...)` | 按油品、金额、日期、站点筛选可用换购方案。 |

### 4.1 已注册的权益计算器

`RuleEngineConfiguration.benefitCalculators()` 将下列计算器注入规则引擎：

- `FixedPriceBenefitCalculator`：固定价；
- `PercentageDiscountBenefitCalculator`：按比例折扣；
- `AmountOffBenefitCalculator`：满减；
- `ExchangePurchaseBenefitCalculator`：加价换购；
- `GiftItemBenefitCalculator`：赠品，并校验赠品库存；
- `GiftCouponBenefitCalculator`：赠券；
- `BundlePriceBenefitCalculator`：组合包价格，并校验组合商品库存；
- `CouponRedeemBenefitCalculator`：优惠券核销；
- `FuelVolumeDiscountBenefitCalculator`：油品按升立减；
- `CompositeBenefitCalculator`：组合权益。

新增规则类型时，应同时补齐规则模型、条件匹配、对应 `BenefitCalculator`、测试用例和导入映射，不能把计算逻辑放入 Controller 或前端页面。

## 5. 主要 API 与前端调用方法

| 业务能力 | 后端接口 | 前端调用方法 |
| --- | --- | --- |
| 服务能力探测 | `GET /api/checkout/capabilities` | `useBackendStatus()` 中直接 `fetch` |
| 促销计算 | `POST /api/checkout/calculate` | `calculateCheckout(request)` |
| 换购方案查询 | `GET /api/checkout/exchange-offers` | `fetchExchangeOffers(params)` |
| 结算确认 | `POST /api/checkout/confirm` | `confirmCheckout(request)` |
| 确认/交易查询 | `GET /api/checkout/confirmations/*`、`GET /api/checkout/transactions/*`、`GET /api/checkout/records/*` | `fetchCheckoutConfirmation()`、`fetchCheckoutTransactions()`、`fetchCheckoutRecords()` |
| 商品查询 | `GET /api/products/search`、`GET /api/products/by-barcode/{barcode}`、`GET /api/products/{productCode}` | `searchProducts()`、`fetchProductByBarcode()`、`fetchProductByCode()` |
| 文件导入 | `POST /api/import/{prices|inventory|promotions|coupons}` | `uploadImportFile(type, file)` |
| 导入批次和异常 | `GET /api/import-batches`、`GET /api/import-batches/{id}/errors` | `fetchImportBatches()`、`fetchImportErrors()`、`exportImportErrors()` |
| 规则治理 | `GET /api/promotion-drafts`、确认草稿、停用规则、审计日志接口 | `fetchPromotionDrafts()`、`confirmDraft()`、`disableRule()`、`fetchAuditLogs()` |
| 库存与预警 | 库存明细、补货、预警和预警处置接口 | `fetchInventoryItems()`、`replenishInventory()`、`fetchInventoryAlerts()`、`markInventoryAlertHandled()` |
| 补货清单 | `POST /api/replenishment/lists`、查询和导出接口 | `createReplenishmentList()`、`fetchReplenishmentList()`、`exportReplenishmentList()` |
| 会员与积分 | 会员识别、会员查询、积分变动、会员券接口 | `identifyMember()`、`fetchMember()`、`changeMemberPoints()`、`fetchMemberCoupons()` |
| 业务日期 | `GET/PUT/DELETE /api/system/business-clock` | `fetchBusinessClock()`、`updateBusinessClock()`、`resetBusinessClock()` |

## 6. 前端页面与路由

| 路由 | 页面 | 主要职责 |
| --- | --- | --- |
| `/checkout` | `CheckoutPage` | 商品录入、油品信息、促销计算、方案选择与结算确认。 |
| `/dashboard` | `DashboardPage` | 展示运营概览。 |
| `/operation-campaigns` | `OperationCampaignPage` | 活动场景验收与券发放操作。 |
| `/import` | `ImportPage` | 上传价格、库存、促销和券文件，查看导入结果。 |
| `/inventory` | `InventoryAlertPage` | 查看库存预警并执行处置或补货。 |
| `/rules` | `RuleManagementPage` | 查看、确认、拒绝或停用促销规则。 |
| `/poster` | `PosterPage` | 演示 AI 海报的提示词、预览和人工审核流程。 |

`App.tsx` 使用 `React.lazy()` 和 `Suspense` 按页面拆分加载；`AppLayout` 使用 React Query 调用业务日期接口，并依据本地保存的演示角色控制菜单可见性。该角色控制仅用于前端体验，不等同于后端认证授权。

## 7. 运行与数据边界

- 后端默认配置不依赖数据库，使用内存实现便于开发和规则测试。
- 启用 `dev-db` 或 `postgres` Profile 后，使用 PostgreSQL、MyBatis 和 Flyway 执行迁移脚本。
- 数据库迁移脚本位于 `backend/src/main/resources/db/migration`，应只追加新版本，不修改已执行版本。
- `data/` 中的 Excel 是原始业务数据源，只读使用，不应由程序或人工直接修改。
- `auth/` 和后端 `poster/` 仍是预留边界；生产部署前需补齐服务端认证、权限控制、密钥管理和外部 AI 服务接入。

## 8. 维护建议

1. 新增促销活动时，先完成 Excel 字段映射与规则结构化，再实现条件与权益计算，最后补充端到端测试。
2. 修改金额、券、库存或交易逻辑时，应同时检查确认流程的幂等性、审计日志和数据库迁移。
3. 前端新增页面时，应通过 `api/` 层调用后端，不复制后端规则判断。
4. 对外部 POS、会员、券和 AI 服务的接入，先定义接口契约、失败兜底和数据安全要求，再进入联调。
