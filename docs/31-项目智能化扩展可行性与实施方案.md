# 项目智能化扩展可行性与实施方案

> 文档日期：2026-07-26
>
> 文档性质：可行性判断与后续实施规划
>
> 评估范围：仅基于当前仓库结构、代码模型、数据库迁移、页面和测试判断；本次不修改任何业务代码。

## 1. 结论摘要

### 1.1 总体结论

**可行，而且当前项目已经具备较好的实施基础。**

最适合本项目的目标不是让大模型直接控制收银，而是建设“季度促销政策智能导入与治理中心”：业务人员上传新的 Excel、Word 或 PDF 政策文件后，系统自动识别活动、商品范围、日期、门槛、权益、互斥关系和适用站点，转换为现有 `PromotionRule` 结构，完成校验、冲突分析和订单仿真，最终生成待审核候选。审核通过后，由待新增的发布包链路原子切换当前生效规则；收银仍只执行后端确认的确定性规则。

建议把“一键导入”定义为：

> 一次上传，自动完成解析、映射、校验、差异对比、仿真和待审候选包生成；只有通过人工审核的规则才允许发布。

不建议把“一键导入”定义为“模型读取文件后直接生效”。促销规则直接影响售价、赠券、赠品、积分、库存和会员权益，模型误读一个小数点、日期或互斥条件就可能产生实际经营损失。**AI 可以缩短录入时间，但不能绕过确定性校验和审批。**

### 1.2 分场景可行性

| 场景 | 可行性 | 当前基础 | 判断 |
| --- | --- | --- | --- |
| 统一模板 Excel 一键生成待审候选 | 高 | 已有 Excel 读取、导入批次、错误行、规则草稿 | 应作为第一期目标 |
| 不同版式 Excel 自动识别列和工作表 | 中高 | 有 EasyExcel 和结构化规则模型 | 需新增模板识别、字段映射和置信度 |
| Word/PDF 自然语言政策转规则草稿 | 中 | 有明确的目标规则结构 | 需文档解析、模型网关、证据定位和评测集 |
| 扫描件政策转规则草稿 | 中低 | 当前无 OCR 能力 | 可后置，且必须人工复核 |
| 自动检查新旧规则冲突和覆盖关系 | 高 | 已有条件、互斥组、优先级和版本 | 近期最值得建设的智能能力之一 |
| 自动用历史订单验证规则影响 | 中高 | 已有计算快照、交易和规则引擎 | 需补齐历史数据质量和仿真服务 |
| 模型直接发布并参与收银 | 技术上可做，业务上不应做 | 已有发布链路 | 不纳入目标范围 |

### 1.3 推荐决策

建议立项，按以下顺序实施：

1. 先把统一模板 Excel 做成稳定的“一键导入到待审候选包”。
2. 同时建设规则校验、差异对比、冲突检测和批量审批，不急于引入大模型。
3. 在确定性流程稳定后，再接入大模型处理非标准 Excel、Word 和 PDF。
4. 最后利用交易、会员和库存数据建设效果评估、补货预测和个性化推荐。

第一阶段即使不接大模型，也能显著减少季度换规则的人工工作量；大模型应当是兼容非标准文件的增强器，而不是整个流程的唯一依赖。

## 2. 判断依据：当前项目已经具备什么

### 2.1 可直接复用的能力

| 现有能力 | 仓库依据 | 对智能导入的价值 |
| --- | --- | --- |
| Excel 文件接收与读取 | `importcenter/ImportCenterController.java`、`EasyExcelWorkbookReader.java` | 可复用上传、临时文件和工作表读取入口 |
| 导入批次与异常行 | `ImportBatch`、`ImportErrorRow`、`ImportRecordApplicationService` | 可追踪每次导入、错误和警告 |
| 通用规则结构 | `PromotionRule`、`PromotionCondition`、`PromotionBenefit` | 已有稳定的目标结构，不需要让模型发明执行格式 |
| 十类促销计算能力 | `PromotionRuleType` 及 `ruleengine/benefit` | 覆盖固定价、折扣、满减、换购、赠品、赠券、组合包、用券、按升立减和复合权益 |
| 丰富的适用条件 | `PromotionCondition` | 已覆盖商品、品类、油品、站点、日期、时段、会员、库存、充值等条件 |
| 确定性规则引擎 | `DefaultPromotionEngine` | AI 生成草稿后可用现有引擎执行，不让模型参与金额计算 |
| 冲突与推荐机制 | `DefaultConflictResolver`、`DefaultCandidateRanker` | 可扩展为新旧规则冲突检查和方案比较 |
| 草稿、确认、停用、归档 | `PromotionRuleGovernanceService` | 已有初步状态流转和审计基础，事务与多版本治理仍需补齐 |
| 规则版本与审计记录 | `promotion_rule_version`、`promotion_rule_audit_log`、`audit_log` | 已有历史留痕基础，但版本表尚未驱动当前规则发布 |
| 手工修正规则保护 | `manualLocked` | 新批次可避免静默覆盖人工确认结果 |
| 批量治理接口 | `batch-confirm`、`batch-revise`、`batch-archive` | 适合季度规则整批审核和换季下线 |
| 收银计算与交易事实 | `checkout_calculation_record`、`checkout_transaction`、`checkout_transaction_item` | 可用于回放仿真和后续效果分析 |
| 商品、库存、会员、券和站点 | 对应领域模块与数据库表 | 可做主数据核验、库存风险和人群范围校验 |
| 前端导入与规则管理入口 | `ImportPage.tsx`、`RuleManagementPage.tsx` | 可在现有工作台上扩展导入向导和审核视图 |
| 自动化测试基础 | `ImportCenterServiceTest`、`PromotionRuleGovernanceServiceTest`、规则引擎测试 | 适合继续构建政策样本回归集和端到端验收 |

当前仓库包含 51 个 Flyway 迁移文件、多个规则引擎与数据库集成测试，说明核心业务模型已经超过概念验证阶段。智能导入无需重写收银计算和规则计算内核；主要工作集中在规则进入系统之前的“理解、规范化、校验、仿真和审批”，同时需要演进规则持久化与运行时加载边界，以支持多版本并存和发布包原子切换。

### 2.2 当前能力的真实边界

现有能力不能直接等同于通用季度规则导入，主要缺口如下：

1. `POST /api/import/promotions` 当前固定调用 `importNinePointNineFixedPricePromotions()`。
2. 当前只读取名为“参考2-9.9元商品专区”的工作表，并按固定表头位置解析。
3. 当前促销导入只生成 `FIXED_PRICE`，其他已支持的规则类型主要来自数据库迁移和手工结构化数据，并没有统一导入映射器。
4. 当前 `stackable` 字段不代表引擎会自动合并多条可叠加规则：现有引擎生成各自候选并推荐其中一个；`COMPOSITE` 也只覆盖当前代码允许的有限组件组合。因此，“跨规则叠加”不能视为已完整支持，无法映射的组合政策必须阻断导入。
5. 当前只能通过扩展名判断 `.xlsx`，还没有文件内容识别、模板版本识别、病毒扫描、压缩炸弹防护和公式安全处理。
6. 当前没有 Word、PDF、OCR 或自然语言政策解析模块。
7. 当前没有模型调用依赖、统一 AI 网关、提示词版本、结构化输出约束、置信度或模型调用审计。
8. 当前规则管理页以逐条查看和确认操作为主，后端虽有批量接口，但还没有完整的季度发布包、差异审核和仿真报告界面。
9. 上传文件会先复制为临时文件，`import_batch.source_file` 记录的可能是临时路径；临时文件随后被删除。当前没有原始文件名、原件归档、文件哈希、模板版本和解析器版本的完整证据链。
10. 当前固定价导入使用 `import-fixed-9_9-{productCode}` 作为规则 ID，而 `promotion_rule_draft.rule_id` 全局唯一。相同商品跨季度重导时可能覆盖同一草稿，或被 `manualLocked` 拦截后继续保留旧规则，不能表达“稳定规则标识 + 季度修订版本”。
11. 现有单条确认、停用、归档和批量操作都会执行多次仓储写入，但服务层没有完整事务边界；日期修订还会通过缩减参数的构造器重建 `PromotionCondition`，可能丢失时段、省区、会员等级/标签、生日月、品类、数量和充值等扩展条件。后续不能在此基础上直接增加自动发布。
12. `promotion_rule_version` 当前只有保存能力，没有完整的版本查询、发布和恢复接口；现有批量操作按规则逐条处理，发生中途失败时可能出现部分更新。
13. 当前收银仓储从 `promotion_rule_draft` 读取 `CONFIRMED` 规则，而不是从版本表或发布包读取。由于 `promotion_rule_draft.rule_id` 全局唯一，同一逻辑规则的旧版生效内容与新版待审内容不能自然并存，不能直接把现有草稿表当作季度多版本发布模型。
14. 日期触发、排除品类、商品组、组合包和库存等信息在运行时动态读取。只保存 `rule_json` 不能保证未来回放得到同一结果，发布和仿真还缺依赖快照。
15. 数据库已有精确站点适用范围等结构，但当前运行时代码仍以站点类型和省区条件为主，尚未形成“政策指定站点清单 -> 规则条件 -> 结算匹配”的完整闭环。
16. 当前 `auth` 后端目录仍是预留边界，操作人信息还可由请求端提供。生产化前必须完成服务端身份认证、可信操作人、角色权限和审批职责分离。
17. 前端文件选择范围与后端格式判断也需统一；后端目前只按文件名后缀接受小写 `.xlsx`，尚未校验真实文件内容。
18. AI 海报页面目前是前端演示数据，没有真正的后端模型服务，不能视为已有 AI 平台能力。

因此，项目的可行性来自“规则与治理底座已经存在”，而不是“通用智能导入已经存在”。

## 3. 目标与边界

### 3.1 目标用户流程

业务人员的理想操作应为：

1. 选择“新季度政策导入”，上传政策文件。
2. 系统自动识别季度、政策版本、工作表或章节，以及规则类型。
3. 系统把政策拆成独立规则，并展示原文出处与结构化结果。
4. 系统自动匹配商品、品类、站点、会员等级和券模板。
5. 系统标出缺失字段、歧义、重复、冲突、毛利和库存风险。
6. 系统用预设订单和历史订单回放规则，生成影响报告。
7. 操作员修正低置信字段，提交复核。
8. 审批人批量确认后生成不可变规则版本和发布包，在生效时间原子切换。
9. 发布后监控异常，需要时一键回退到上一发布包。

### 3.2 明确不做的事情

- 不让大模型直接计算应付金额或替代 `ruleengine`。
- 不允许模型直接写数据库、生成 SQL 或修改 Flyway 历史。
- 不允许含歧义的金额、日期、数量、商品范围自动补猜后发布。
- 不允许上传即进入 `CONFIRMED` 状态。
- 不允许未经批准把政策全文、会员信息或交易明细发送到外部模型。
- 不把“解析成功”当作“业务规则正确”，必须经过校验和仿真。

## 4. 建议的总体架构

~~~mermaid
flowchart LR
    A["上传季度政策文件"] --> B["文件安全检查与去重"]
    B --> C["格式和模板识别"]
    C --> D{"标准模板?"}
    D -->|是| E["确定性 Excel 解析器"]
    D -->|否| F["文档解析与模型结构化抽取"]
    E --> G["统一政策中间模型"]
    F --> G
    G --> H["字段与主数据校验"]
    H --> I["新旧规则差异和冲突检测"]
    I --> J["规则引擎订单仿真"]
    J --> K["待审规则包与风险报告"]
    K --> L{"人工审批"}
    L -->|退回| M["人工修正或重新解析"]
    M --> H
    L -->|通过| N["生成规则版本并定时发布"]
    N --> O["运行监控、审计与回滚"]
~~~

### 4.1 核心原则

1. **规则引擎保持确定性。** 模型只负责理解输入，所有金额和权益仍由现有 Java 计算器计算。
2. **标准模板优先。** 能用固定字段可靠解析的内容，不调用大模型。
3. **先形成中间模型，再转换为 `PromotionRule`。** 中间模型保留原文、出处、置信度和未决项，避免过早丢失信息。
4. **字段级可追溯。** 每个关键字段能定位到工作表、行列、页码或原文片段。
5. **失败应显式。** 无法确认的内容进入 `BLOCKER` 或 `WARNING`，不得静默跳过或猜测。
6. **模型可替换。** 通过统一网关隔离具体模型供应商或私有化部署方案。
7. **发布包原子化。** 一个季度的一组规则要么整体发布成功，要么保持上一版本，不留半更新状态。

### 4.2 建议新增的模块边界

不建议把模型调用直接塞入现有 `ImportCenterService`。可按当前领域分层方式规划：

~~~text
backend/src/main/java/com/cnpc/promoretail/
  importcenter/                 保留文件上传、批次和通用错误记录
  policyingestion/             新增：季度政策导入编排
    api/                       导入任务、预览、校验、仿真、提交接口
    application/               工作流与状态机
    parser/                    Excel、DOCX、PDF、OCR 适配器
    normalization/             中间模型到 PromotionRule 的转换
    validation/                结构、语义、主数据、冲突和财务校验
    simulation/                规则引擎回放与报告
    persistence/               解析证据、校验问题和发布包
  ai/                          新增：模型网关、结构化输出和调用审计
  promotion/                   复用现有草稿、版本、审批和归档
  ruleengine/                  继续作为唯一促销执行与金额计算内核
~~~

前端优先扩展现有导入页和规则管理页；当流程复杂度上升后，再拆出“政策导入工作台”和“发布包详情页”。

## 5. 统一政策中间模型

### 5.1 为什么不能让模型直接输出现有规则 JSON

现有 `PromotionRule` 是执行模型，适合准确数据，不适合承载“原文有歧义”“商品尚未映射”“日期来自标题”等解析状态。若模型直接输出执行 JSON，后续很难回答某个金额来自哪一格，也无法区分政策原文缺失与模型未识别。

建议新增 `PromotionPolicyIR` 作为导入中间模型，审核完成后再转换为 `PromotionRule`。建议至少包含：

~~~json
{
  "policyPackageId": "2026-Q4-xinjiang-v1",
  "sourceDocumentId": "document-id",
  "ruleKey": "source-stable-key",
  "activityName": "会员日满减",
  "ruleType": "AMOUNT_OFF",
  "conditions": {},
  "benefit": {},
  "priority": 50,
  "exclusiveGroup": "direct_discount",
  "stackable": false,
  "effectivePeriod": {
    "startDate": "2026-10-01",
    "endDate": "2026-12-31"
  },
  "evidence": [
    {
      "location": "活动汇总!G12",
      "text": "会员消费满100减20"
    }
  ],
  "fieldConfidence": {
    "ruleType": 0.99,
    "conditions.minCartAmount": 0.98,
    "benefit.amountOff": 0.98
  },
  "unresolvedFields": []
}
~~~

`ruleKey` 应优先使用政策发布方给出的稳定活动代码和子规则代码。没有业务编码时，应建立经过人工确认的持久身份映射；适用范围变化或表格行移动不能导致一条 `CHANGED` 规则被误判成 `NEW + REMOVED`。文件哈希用于识别同一文件，单元格和页码只作为证据，二者都不能替代业务规则身份。

`fieldConfidence` 不能直接采用模型自报分数。它应由字段来源、Schema 校验、主数据匹配、解析器类型和黄金集表现共同校准，只用于风险分流；是否可发布仍由确定性校验和审批闸门决定。

### 5.2 关键字段处理规则

| 字段类别 | 处理策略 |
| --- | --- |
| 金额、折扣率、数量 | 必须从明确单元格或原文抽取；禁止模型自行换算后覆盖原值 |
| 日期和时段 | 同时保存原文和标准值；跨年、跨午夜和“节假日期间”必须专项校验 |
| 商品编码 | 以主数据精确匹配为主；名称模糊匹配只能作为候选，不能直接确认 |
| 品类和排除项 | 映射到现有品类词典；“烟、化肥除外”等否定条件必须单独保留 |
| 站点范围 | 映射到站点 ID、站点类型或省区，不能只保存自由文本 |
| 会员条件 | 映射会员身份、等级、标签、生日月等现有字段 |
| 权益 | 必须映射到现有规则类型和计算器；无法映射的内容标为不支持 |
| 叠加和互斥 | 原文没有说明时不得默认可叠加；还必须通过执行语义覆盖矩阵，不能仅设置 `stackable` |
| 优先级 | 可按组织规则给出建议值，但必须展示依据并允许审批人调整 |

## 6. 智能导入流水线

### 6.1 文件接收与安全检查

- 校验真实 MIME 类型和文件签名，不只检查扩展名。
- 对文件大小、工作表数、行数、压缩比和解析耗时设置上限。
- 进行恶意文件扫描、公式注入和压缩炸弹防护。
- 计算 SHA-256，识别重复上传和同源文件的新版本。
- 原文件只读保存，记录上传人、时间、来源单位和政策编号。
- 政策内容按不可信输入处理，禁止其中的文本改变模型系统指令或触发工具执行。

### 6.2 格式和模板识别

解析顺序建议固定为：

1. 已注册模板和版本的确定性解析器。
2. 可配置列映射器，例如“商品编码/货号/SKU”映射到同一字段。
3. 对剩余无法识别的表格或正文使用模型结构化抽取。
4. 扫描件最后才进入 OCR，并始终提高风险等级。

模板注册表应包含模板 ID、版本、工作表特征、表头指纹、起始行、字段映射、适用规则类型和解析器版本。业务方改列名时，系统可以识别为“疑似新版本”，而不是导入出一批错误规则。

### 6.3 模型结构化抽取

模型网关只接受经过清洗的文本、表格片段和允许的主数据摘要，输出必须通过 JSON Schema 校验。建议要求模型同时返回：

- 识别出的规则类型；
- 条件和权益字段；
- 每个字段的来源位置和原文；
- 字段级置信度；
- 无法确定的问题列表；
- 可能涉及但当前引擎不支持的业务语义。

模型输出不得直接写入 `promotion_rule_draft`。通过规范化和校验的结果仍先保存在候选层；只有走完审批和发布流程后，才能形成不可变规则版本并更新当前生效投影。全新规则可通过兼容适配复用现有草稿流程，但既有规则的新修订不能在审批前覆盖当前 `CONFIRMED` 投影。

### 6.4 确定性校验

建议建立六层校验：

| 层级 | 典型检查 | 失败处理 |
| --- | --- | --- |
| 文件层 | 文件损坏、模板不匹配、超限、重复文件 | `BLOCKER` |
| 结构层 | 必填字段、数据类型、范围、小数位 | `ERROR` 或 `BLOCKER` |
| 主数据层 | 商品、品类、站点、券模板、会员等级是否存在 | 精确缺失为 `BLOCKER`，模糊候选为待确认 |
| 语义层 | 满减门槛大于优惠额、折扣率合法、日期前后关系、权益与类型一致 | `ERROR` |
| 治理层 | 重复规则、覆盖人工锁定规则、新旧版本替代关系 | `WARNING` 或 `BLOCKER` |
| 行为层 | 代表性订单能否命中、边界金额是否正确、库存不足是否阻断 | 仿真失败禁止发布 |

每种政策语义都应登记“执行语义覆盖矩阵”，至少列出目标规则类型、所需条件、权益计算器、叠加/互斥行为、动态依赖和黄金测试。只有模型字段能解析出来但现有引擎不能等价执行时，仍应标记为 `BLOCKER`。尤其不能把 `stackable=true` 当作多规则合并已经实现，也不能把有限的 `COMPOSITE` 能力当作任意权益组合。

关键业务数值的验收原则应是“能确认则精确转换，不能确认则阻断”，而不是用低置信度结果勉强完成导入。

统一闸门定义为：`BLOCKER` 和未解决的 `ERROR` 都禁止提交审批或发布；`WARNING` 不自动阻断，但必须由具备权限的复核人逐项确认或填写豁免理由，并进入审计记录。

### 6.5 新旧规则差异和冲突检测

季度换规则时，系统应按稳定 `ruleKey` 输出四类结果：

- `NEW`：本季度新增；
- `CHANGED`：条件、权益、范围或优先级发生变化；
- `UNCHANGED`：内容相同，可继续沿用；
- `REMOVED`：上季度存在、本季度未出现，需确认停用或归档。

冲突检测至少覆盖：

- 同一商品、同一时间和同一范围内出现多个不可叠加优惠；
- 同一规则 ID 内容变化但未形成新版本；
- 新规则覆盖 `manualLocked` 规则；
- 新旧有效期重叠或出现空档；
- 固定价高于现价、优惠额超过订单金额、折扣率越界；
- 赠品或组合包商品不存在、库存长期不足；
- 券门槛、券有效期和活动有效期不一致；
- 站点、会员或省区范围为空导致意外全量适用；
- `REMOVED` 规则仍处于 `CONFIRMED`。

### 6.6 订单仿真

仿真应直接调用现有 `DefaultPromotionEngine`，不另写一套计算逻辑。用例分为三组：

1. **自动边界用例**：门槛前一分、正好门槛、门槛后一分；开始日前、开始日、结束日、结束日后；数量少一件、正好、超一件。
2. **标准业务用例**：匿名顾客、不同会员等级、不同站点、不同油品和不同库存状态。
3. **历史订单回放**：抽取真实交易的脱敏上下文，同时在旧规则包和新规则包上运行，比较命中率、让利额、毛利风险和阻断原因。

仿真报告需要同时展示新旧结果、使用的规则版本和差异原因。历史回放只能作为决策依据，不能代替业务验收。

回放不能读取“今天”的动态依赖来解释过去。每个发布包应冻结或引用可追溯版本的日期触发、排除品类、商品组、组合包、券模板等配置；历史订单还应使用交易发生时的价格和库存上下文。否则同一规则 JSON 在依赖数据变化后无法复现，也无法可靠验证回滚。

## 7. 数据模型规划

应复用现有 `import_batch`、`import_error_row`、`promotion_rule_draft`、`promotion_rule_version`、`promotion_rule_audit_log` 和通用 `audit_log`，避免建立第二套规则治理表。

建议新增或扩展以下概念，具体字段在详细设计阶段确定：

| 概念 | 用途 | 与现有模型关系 |
| --- | --- | --- |
| `policy_source_document` | 保存文件元数据、哈希、政策编号、季度和存储位置 | 关联 `import_batch` |
| `policy_parse_run` | 记录解析器/模型、模板版本、提示词版本、状态和耗时 | 一个文件可多次解析 |
| `promotion_rule_identity` | 保存稳定逻辑规则键和无业务编码时的人工确认映射 | 与季度、来源坐标和执行版本解耦 |
| `policy_rule_candidate` | 保存中间模型、置信度、证据和未决项 | 审批前不覆盖当前生效投影 |
| `policy_field_evidence` | 保存字段到单元格、页码或原文的映射 | 支撑审核和审计 |
| `rule_validation_issue` | 保存校验等级、问题代码、修复状态和责任人 | 可复用现有错误等级语义 |
| `rule_diff_record` | 保存新旧字段差异和替代关系 | 连接当前规则版本 |
| `rule_simulation_run` | 保存用例集、规则包、结果摘要和失败项 | 调用现有规则引擎 |
| `rule_simulation_input_snapshot` | 保存回放时的订单、价格、库存和站点上下文版本 | 通过快照 Provider 注入，不读取当前实时值 |
| `promotion_release_package` | 将一个季度的规则作为原子发布单元 | 包含多个已确认版本 |
| `promotion_release_item` | 保存发布包内每条规则的启用、替换或退役动作 | 指向不可变规则修订/版本 |
| `promotion_release_dependency_snapshot` | 冻结日期触发、排除品类、商品组、组合包等依赖版本或内容哈希 | 保证回放和回退可复现 |
| `promotion_active_release` | 保存当前生效发布包或等价指针 | 供运行时原子切换和回退 |
| `ai_invocation_audit` | 保存模型、版本、输入摘要、输出哈希、令牌/耗时和结果状态 | 不保存不必要的敏感明文 |

目标模型需要允许“旧版仍在生效、新版正在待审”同时存在。建议采用“稳定逻辑规则键 -> 不可变候选/修订 -> 发布项 -> 当前发布包指针”的结构，并让运行时仓储最终按当前发布包读取规则版本。迁移期间可以维护兼容投影同步到现有 `promotion_rule_draft`，但不能继续依赖覆盖同一 `rule_id` 完成换季。规则回退应切换到上一发布包并生成新的审计动作，而不是删除历史版本。

发布包回退只影响回退完成后的新结算，不能自动撤销已经完成的交易、已发券/积分或库存变化。生产事故流程还应支持定位受影响交易、停止后续发放、在业务规则允许时冻结未使用权益、生成补偿方案、双人审批和财务对账；禁止通过删除交易或直接反向改数来伪造回退。

## 8. 接口和前端工作台规划

### 8.1 后端接口草案

| 接口 | 作用 |
| --- | --- |
| `POST /api/policy-imports` | 上传政策并创建异步任务 |
| `GET /api/policy-imports/{id}` | 查询任务状态和摘要 |
| `GET /api/policy-imports/{id}/candidates` | 查询结构化候选规则和证据 |
| `PATCH /api/policy-imports/{id}/candidates/{ruleKey}` | 修正待确认字段 |
| `POST /api/policy-imports/{id}/validate` | 重新执行确定性校验 |
| `POST /api/policy-imports/{id}/simulate` | 发起订单仿真 |
| `GET /api/policy-imports/{id}/diff` | 查看与当前生效规则的差异 |
| `POST /api/policy-imports/{id}/submit` | 生成待审批规则包 |
| `GET /api/promotion-releases` | 查询当前发布包、历史版本和状态 |
| `POST /api/promotion-releases/{id}/approve` | 记录独立复核人的审批结论 |
| `POST /api/promotion-releases/{id}/schedule` | 由发布角色安排原子生效时间 |
| `POST /api/promotion-releases/{id}/rollback` | 回退到上一发布包 |

解析和仿真可能耗时，应采用异步任务并允许前端轮询或使用服务端事件。所有改变状态的接口都应具备幂等键和权限校验。

### 8.2 前端导入向导

建议采用六步工作流：

1. **上传**：显示支持格式、安全检查和文件摘要。
2. **识别**：显示政策季度、模板、工作表/章节和解析方式。
3. **映射**：逐条展示规则结构、原文证据、置信度和主数据候选。
4. **校验**：按 `BLOCKER / ERROR / WARNING` 分类处理问题。
5. **仿真与差异**：查看新旧规则、边界用例和历史订单影响。
6. **提交审批**：生成不可变规则包，审批后定时发布。

页面应把“AI 建议”“系统校验通过”“人工已确认”显示为三个不同状态，避免用户把模型置信度误解成业务正确性。

## 9. 分阶段实施计划

以下工期是假设 2 名后端、1 名前端、1 名测试，以及产品/促销业务人员兼职参与的粗略估算；在模板和审批口径确认后需要重新排期。

### 阶段 0：规则契约与生产前置，2 至 3 周

目标：先建立安全、可评测的入口。

- 选定首个季度政策模板和支持的规则类型。
- 定义 `PromotionPolicyIR`、JSON Schema、字段词典和错误代码。
- 建立文件哈希、模板版本和幂等策略。
- 区分稳定业务 `ruleKey`、季度修订和执行版本，明确全量导入与增量导入的语义。
- 建立执行语义覆盖矩阵，逐项确认规则类型、条件、计算器、叠加行为、动态依赖和测试覆盖。
- 将修订契约定义为不可变全量副本或经过 Schema 约束的字段级 Patch，禁止用缩减构造器重建规则；任何字段修订都必须证明未涉及条件完整保留。
- 设计发布包级事务、乐观锁和失败恢复机制，避免一批规则只成功一部分。
- 补齐服务端认证、角色权限和操作人可信来源，至少分离导入、复核、发布和审计权限。
- 准备至少三个历史季度的脱敏政策样本和人工标注真值。
- 建立解析、规则转换和边界订单的黄金测试集。

出口条件：输入、输出、审批责任和不支持范围都有书面契约。

### 阶段 1：标准 Excel 一键导入到候选包，4 至 6 周

目标：不依赖大模型，先在影子模式交付高可靠的解析、校验和最小仿真。

- 建立模板注册和通用字段映射机制。
- 覆盖优先级最高的规则类型：固定价、折扣、满减、换购、赠品、赠券和组合包。
- 接入商品、品类、精确站点范围、会员和券模板主数据校验。
- 生成导入候选、错误报告和待审规则包；在多版本模型完成前不覆盖当前 `PromotionRuleDraft` 生效投影。
- 增加重复导入、人工锁定保护、新旧规则差异和最小静态冲突检查。
- 为金额、日期和数量自动生成边界订单，并调用现有规则引擎仿真。
- 在前端完成批量预览、修正和提交审批。

出口条件：受支持模板可“一次上传生成完整待审候选包、差异和边界仿真报告”，任何异常都不会进入当前生效规则。

### 阶段 2：发布治理与生产闭环，3 至 5 周

目标：在引入模型前，先解决多版本并存、原子发布和恢复问题。

- 建设稳定规则身份、不可变修订、发布项和当前发布包指针。
- 改造运行时仓储，使收银按当前发布包加载规则版本，而不是以草稿表作为版本发布源。
- 为单条治理和整包发布建立事务边界；建设双人审批、定时生效、预期版本校验、乐观锁和原子切换。
- 为日期触发、排除品类、商品组、组合包和券模板等动态依赖生成发布快照或不可变版本引用。
- 增加历史订单回放、库存与让利风险报告；价格、库存等动态输入通过版本化快照 Provider 注入。
- 支持灰度站点验证、异常阈值告警和上一发布包回退。
- 建设受影响交易定位、权益停发/冻结、补偿审批和财务对账流程。
- 完成版本历史、发布记录和回退结果查询。

出口条件：标准模板导入可以安全进入生产，且失败时不会留下半发布状态，可恢复上一稳定发布包。

### 阶段 3：非标准文件智能理解，4 至 6 周

目标：在确定性治理闭环之上兼容列名变化、复杂表格、DOCX 和文本型 PDF。

- 建立可替换的模型网关和私有化/企业模型适配器。
- 实现文档切分、表格保真抽取、受控提示词和 JSON Schema 输出。
- 保存字段证据、置信度、模型版本和调用审计。
- 对商品名称、品类和站点提供候选匹配，不自动确认模糊结果。
- 建立模型离线评测、回归阈值和失败降级。
- 扫描件 OCR 仅在样本需求明确后作为可选项加入。

出口条件：模型升级或提示词变化必须通过同一黄金集，低置信结果全部进入人工复核，并复用阶段 1 和阶段 2 的校验、仿真与审批闸门。

### 阶段 4：运营决策智能化，持续演进

目标：从“正确执行政策”走向“辅助制定更有效的政策”。

- 促销效果归因和活动复盘。
- 需求预测与活动备货建议。
- 会员分群与下一最佳优惠建议。
- 异常交易、券滥用和规则效果漂移检测。
- 基于已确认规则生成受控营销物料。

若模板、历史样本和审批口径能在启动时到位，阶段 0 与阶段 1 可部分并行，影子模式内部试点合理预期为 7 至 9 周；完成阶段 2 的标准模板生产版本合理预期为 10 至 14 周；包含阶段 3 非标准文档智能理解的版本合理预期为 14 至 18 周。该估算用于立项，不是固定交付承诺，详细排期应在样本盘点后确定。

## 10. 验收标准

### 10.1 第一阶段验收

| 指标 | 建议门槛 |
| --- | --- |
| 支持模板识别 | 黄金样本 100% 正确识别模板版本 |
| 关键数值准确性 | 金额、折扣率、数量和日期在黄金集上 100% 精确 |
| 规则转换覆盖 | 受支持规则中至少 95% 自动形成候选，其余必须有明确错误 |
| 主数据校验 | 不存在的商品、站点、券模板 100% 被拦截 |
| 未审核规则隔离 | 100% 保持非 `CONFIRMED`，不得参与收银 |
| 幂等性 | 同一文件重复提交不产生重复生效规则 |
| 可追溯性 | 每个关键字段均可回到原文件位置 |
| 人工锁定保护 | 自动导入不能覆盖 `manualLocked` 规则 |

### 10.2 智能解析验收

- 模型原始输出可以留存在解析审计中，但 100% 经过 Schema 和领域校验后才可标记为有效候选。
- 金额、日期、数量、商品范围、适用人群和叠加关系等关键字段在黄金集上精确匹配，关键字段错误却被接受的数量为 0。
- 非关键规范化字段建议达到 precision 不低于 99%、recall 不低于 95%；原文证据定位正确率不低于 99%。
- 黄金集中已知“不支持语义”的识别召回率为 100%，不得转换成近似但不可等价执行的规则。
- 建议最低评测集覆盖每一种拟支持规则类型不少于 30 条，并各含不少于 10 条边界、歧义或不支持样本；总条款数不少于 300，且来自至少三个季度。
- `fieldConfidence` 必须用黄金集校准风险分段，不以模型自报分数作为上线依据；持续统计高、中、低风险段的实际正确率和人工修正率。
- 模型、提示词或解析器升级未通过同一黄金集时禁止上线；重复评测比较规范化字段的语义一致率和漂移阈值，不要求生成文本逐字一致。
- 模型不可用时，标准模板导入和现有收银计算继续工作。

### 10.3 发布验收

- 一个发布包中存在 `BLOCKER` 或未解决的 `ERROR` 时不可审批、排期或发布；`WARNING` 只有在授权复核人填写理由后才能豁免。
- 发布前必须通过边界用例和指定历史订单回放。
- 审批人不能与提交人相同，生产权限由后端校验。
- 发布、停用、归档和回滚均记录操作者、原因、规则版本和前后快照。
- 使用同一订单快照、规则版本和依赖快照重复回放时，核心金额与命中结果完全一致。
- 可在 5 分钟内完成上一稳定发布包的逻辑回退。
- 回退报告明确说明只影响后续结算，并列出已完成交易、已发权益和库存影响的处置或补偿状态。

## 11. 测试与评测策略

1. **解析器单测**：每个模板版本、合并单元格、空行、继承值、异常数值和列名变体。
2. **规则契约测试**：中间模型到 `PromotionRule` 的一一映射和不支持语义。
3. **规则引擎回归**：复用现有计算器测试，新增导入后端到端用例。
4. **属性与边界测试**：金额、日期、数量门槛的前后边界；按规则类型定义不变量，例如金额非负、固定价精确、门槛行为符合政策，不假设所有促销都具备整体单调性。
5. **冲突测试**：互斥组、叠加、优先级、新旧有效期和人工锁定。
6. **模型黄金集**：政策原文、人工标注结构、证据位置和预期问题等级。
7. **对抗测试**：提示注入、隐藏文字、复杂表头、歧义单位、同名商品和恶意文件。
8. **可复现性测试**：依赖主数据变化后，旧发布包使用自身快照仍能得到原结果。
9. **故障测试**：模型超时、重复回调、数据库失败、发布中断和回滚。
10. **影子运行**：新版本先只生成报告，不影响收银；与人工维护结果连续比对至少一个完整导入周期。

生产监控至少包含解析成功率、人工修正率、低置信字段率、校验问题分布、仿真失败率、导入耗时、模型成本、发布后异常折扣率和回滚次数。

## 12. 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 模型幻觉或漏读否定条件 | 错误优惠或范围扩大 | 字段证据、关键值精确校验、低置信阻断、人工审批 |
| Excel 模板季度变化 | 批量错列 | 模板指纹和版本注册，未知模板不自动套用旧映射 |
| 重复或覆盖历史规则 | 同一活动重复执行 | 文件哈希、稳定 `ruleKey`、差异检测、`manualLocked` 保护 |
| 草稿表同时承担当前投影 | 旧版生效与新版待审无法并存 | 独立候选/修订、发布项和当前发布包指针 |
| 批量发布中途失败 | 新旧规则混合生效 | 发布包级事务、幂等、乐观锁和故障回退 |
| 动态依赖未随版本冻结 | 历史回放和回退结果不可复现 | 发布依赖快照、内容哈希和按时间点读取 |
| 新旧规则冲突 | 叠加错误或优惠超预算 | 静态冲突分析和订单仿真 |
| 外部模型数据泄露 | 企业数据与会员隐私风险 | 优先私有化或批准的企业模型，最小化输入、脱敏、加密和审计 |
| 文档提示注入 | 模型被文件内容误导 | 将文件视为数据、固定系统指令、Schema 输出、禁用工具和网络访问 |
| 模型升级漂移 | 同一政策解析结果改变 | 固定版本、离线黄金集、灰度和可回退 |
| 历史数据质量不足 | 效果预测失真 | 数据质量评分，先做规则正确性再做预测，报告置信区间 |
| 自动化造成责任不清 | 无法追责 | 提交、审批职责分离，所有修改留存人和理由 |
| 模型服务故障 | 导入阻塞 | 异步任务、重试、熔断；标准模板路径不依赖模型 |

## 13. 其他值得建设的智能化方向

### 13.1 优先级建议

| 方向 | 业务价值 | 当前数据/结构准备度 | 实施难度 | 建议优先级 |
| --- | --- | --- | --- | --- |
| 规则质量检查与冲突解释 | 高 | 高 | 中 | P0，与智能导入同步 |
| 促销发布前订单仿真 | 高 | 中高 | 中 | P0/P1 |
| 规则解释与排障助手 | 中高 | 高 | 中低 | P1 |
| 促销效果分析与复盘助手 | 高 | 中 | 中高 | P1 |
| 库存需求预测与智能补货 | 高 | 中 | 中高 | P1 |
| 异常折扣、券滥用检测 | 高 | 中 | 中高 | P1 |
| 会员下一最佳优惠 | 中高 | 中 | 高 | P2 |
| AI 营销海报与文案 | 中 | 低，当前仅前端演示 | 中 | P2 |

### 13.2 规则质量检查与冲突解释

这是除导入外最适合当前项目的创新点。现有规则结构、互斥组、优先级、阻断原因和审计已经具备，先用确定性算法找出冲突，再用模型把结果解释给业务人员。例如：“新季度的会员日九折与 9.9 元固定价在 10 月 9 日同时适用于商品 A，二者都不可叠加，按当前优先级固定价胜出。”

这项能力数据要求低、风险可控，能直接降低规则配置错误。

### 13.3 规则解释与排障助手

现有收银结果已经包含命中说明、阻断原因和规则版本，后续可提供只读问答入口，回答“这笔订单为什么没有命中会员日”“再购买多少可以参加满减”“当前用了哪个版本的规则”等问题。答案中的金额、门槛和状态必须来自规则引擎结果、规则快照和审计数据，模型只负责组织语言，并附可核对的规则和政策来源。

该助手不得修改购物车、规则或券状态，也不能把“怎样才能命中”表述为对顾客的强制销售指令。它适合为收银员和运营人员降低排障成本。

### 13.4 促销效果分析与复盘助手

基于 `checkout_transaction`、交易明细、确认候选和规则版本，形成活动前后对比：参与率、销售额、客单价、让利额、关联购买、券领取与核销、缺货损失等。模型负责生成可读摘要，指标由 SQL 或分析服务确定性计算。

必须避免简单把活动期间增长全部归因于促销。成熟阶段应采用对照站点、同期基线或 A/B 试验，并同时展示置信区间和样本量。

### 13.5 库存预测与智能补货

现有库存预警与补货模块使用固定安全阈值和公式，后续可结合站点、星期、节假日、促销规则、历史销量和到货周期预测需求，给出活动前备货量及缺货概率。

第一步应是“建议模式”，由站长确认，不直接下采购单。需要先确保库存快照频率、销售流水、退货和到货数据完整。

### 13.6 异常交易与券风险检测

利用结算、会员、券和审计数据识别短时间重复核销、异常高优惠率、同一会员跨站集中领券、规则上线后让利突增等情况。优先采用规则阈值和统计异常检测，大模型仅用于解释告警和汇总处置建议。

### 13.7 会员下一最佳优惠

结合会员等级、标签、消费频率、油品偏好和券使用行为推荐合适的促销，而不是一味推荐折扣最高的活动。目标函数应同时考虑顾客价值、毛利、库存和券成本，并提供退出个性化和人工干预机制。

该方向需要更长时间跨度的高质量交易数据和严格的数据权限，因此不应早于智能导入和效果分析建设。

### 13.8 受控 AI 海报

当前 `PosterPage` 已有演示流程，但没有后端模型服务。后续可以从已确认规则自动生成海报草稿，价格、日期、商品和限制条件由系统锁定为不可修改字段，模型只负责版式和非关键文案；发布前仍需人工审核。相比规则导入，这项功能更直观，但对核心收银正确性的贡献较低，建议后置。

## 14. 建议的立项边界与下一步

### 14.1 首个版本建议范围

首个试点版本只支持一种经过确认的季度 Excel 模板，并覆盖当前最常见的七类促销：固定价、折扣、满减、换购、赠品、赠券和组合包。试点交付“一键生成待审候选包、差异报告和边界仿真”，以影子模式和人工配置结果对比；暂不支持扫描件，不做无人审核发布，不做个性化自动决策。通过阶段 2 的多版本与发布治理验收后，才进入生产收银规则链路。

这个范围能最大程度复用现有结构，也能最快验证业务价值。

### 14.2 立项前必须由业务方确认的事项

1. “一键导入”的终点是否同意定义为待审规则包，而不是直接生效。
2. 哪一份文件是下一季度的正式模板，是否存在 Word/PDF 补充条款。
3. 首期需要覆盖的规则类型和明确不支持的特殊活动。
4. 商品、站点、券模板和会员等级的主数据权威来源。
5. 促销提交人、复核人、发布人和回滚人的职责划分。
6. 是否允许调用外部模型；若不允许，确定私有化部署和算力边界。
7. 能否提供至少三个历史季度的政策、人工配置结果和脱敏交易样本。
8. 毛利、券成本、赠品成本和预算红线是否可被系统读取。

### 14.3 Go / No-Go 条件

满足以下条件即可进入实施：

- 有稳定的首期模板和业务负责人；
- 现有规则类型能够覆盖首期大部分政策；
- 接受“AI 生成草稿，人工审批发布”的治理原则；
- 能提供主数据和历史样本用于校验；
- 生产前愿意补齐后端认证、权限和审计要求。

如果业务坚持“任意文件上传后无人审核直接生效”，则建议暂缓。该目标虽然技术上可以实现，但不符合当前项目涉及真实价格和权益的风险等级。

## 15. 最终建议

本项目最合理的智能化路线是：

> **先把规则变更做成可验证、可解释、可审批、可回滚的自动化流程，再在这个安全底座上增加大模型理解、效果预测和运营推荐。**

当前项目的规则模型、执行引擎、版本治理、审计、交易和库存模块已经为这条路线提供了基础。优先建设标准 Excel 一键导入、规则冲突检查和发布前仿真，投入产出比高；非标准文档理解、个性化推荐和生成式海报适合作为后续增强，而不应阻塞第一阶段落地。
