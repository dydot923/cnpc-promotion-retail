## 一、计划结论

下一步开发只聚焦一个目标：把当前由前端自报角色、自报操作人的演示型权限，改造成由服务端签发身份、服务端执行权限、服务端记录真实操作人的可信闭环。

选择本任务作为下一步，理由如下：

1. `00-mimo产品文档.md` 和 `20-doubao-核心产品需求文档.md` 都定义了四类角色及权限矩阵，且明确要求用户登录、密码哈希、会话超时、数据隔离和关键操作审计。
2. 27号清单中的充值、会员生命周期发券、排除品类、积分兑换与抽奖等缺口，已被 V28-V33 迁移及对应服务、接口和测试大幅覆盖，不应继续按旧状态重复开发。
3. 当前 `auth` 模块只有 `package-info.java`，`pom.xml` 没有 Spring Security 依赖，所有业务接口默认可直接访问。
4. 前端可通过 `localStorage` 和角色下拉框切换身份，`apiRequest` 不携带认证凭证；结算、规则管理和运营发券中的操作人工号仍由前端硬编码或手工输入。
5. 规则确认、数据导入、券发放、积分抽奖、库存处置等写操作已经具备真实业务影响。在继续开发 AI 海报、报表或系统配置前，必须先建立可信身份边界。

因此，DEV-28 完成前，不新增新的促销类型，不扩展 AI 海报真实生成，不启动报表中心开发。

### 2.2 当前安全缺口

| 缺口 | 代码证据 | 影响 |
|------|----------|------|
| 无认证实现 | `backend/.../auth/package-info.java` 只有包声明 | 任意调用方都可访问业务接口 |
| 无服务端授权 | `backend/pom.xml` 无 Spring Security | 角色矩阵只停留在文档和前端展示层 |

| 操作人可伪造 | 收银、规则、库存、运营接口由请求体或查询参数提交 `operatorId/operatorName` | 审计日志不能证明真实操作者 |

| 缺少站点身份约束 | 收银请求可自行提交站点编码 | 门店角色可能操作其他站点数据 |

## 三、目标与成功标准

### 3.1 业务目标

1. 用户使用账号和密码登录，后端返回短期访问令牌并维护可撤销的刷新会话。
2. 后端按角色和站点范围保护每个接口，前端菜单权限只作为交互提示。
3. 所有关键业务操作从认证上下文取得操作人，不再信任请求端提交的操作人工号或姓名。
4. 系统管理员可以创建、停用、解锁账号并重置密码；区域运营只能管理其授权范围内的门店账号。
5. 登录、失败登录、退出、账号变更、规则变更、导入、结算确认、发券和库存处置均可追溯到真实用户。

### 3.2 可度量成功标准

| 编号 | 标准 |
|------|------|
| S-01 | 未登录访问受保护接口统一返回 HTTP 401 和标准 `ApiResponse` 错误体 |
| S-02 | 已登录但无权限访问统一返回 HTTP 403，不泄露目标数据 |
| S-03 | 四类角色的允许/拒绝矩阵均有自动化测试 |
| S-04 | 客户端伪造 `operatorId`、`operatorName` 或角色字段不会改变审计身份 |
| S-05 | 密码仅保存 BCrypt 哈希，日志、API、迁移脚本和前端存储中均无明文密码 |
| S-06 | 刷新令牌轮换、退出撤销、账号停用、密码重置后旧会话失效 |
| S-07 | 收银员和店长不能越权访问未授权站点的写操作 |
| S-08 | 前端无角色切换器，刷新页面可恢复登录态，退出后受保护页面不可访问 |
| S-09 | V1-V35 空库迁移、后端专项及全量测试、前端测试和生产构建全部通过 |
| S-10 | 手机号等敏感信息默认脱敏；查看完整值需要独立权限并写入审计 |

### 5.4 令牌与会话状态机

1. 使用 Spring Security 的无状态访问令牌校验；访问令牌建议 15 分钟有效。
2. 刷新令牌使用高强度随机值，数据库只保存哈希；通过 `HttpOnly`、`SameSite=Strict` Cookie 传递，并在生产环境启用 `Secure`。
3. `must_change_password=true` 的账号登录后只获得5分钟受限令牌，不签发刷新 Cookie；该令牌只允许修改本人密码和退出。改密成功后令牌失效，用户重新登录获取正常会话。
4. `POST /api/auth/logout` 可在访问令牌过期时仅凭刷新 Cookie 撤销会话并清除 Cookie；无 Cookie 时保持幂等成功，不要求先刷新访问令牌。
5. 刷新令牌每次使用后轮换。前端使用 Web Locks 或等价跨标签页互斥，并通过 `BroadcastChannel` 共享刷新结果；服务端对同一会话行加锁，只允许一个成功后继。短暂并发重放返回明确冲突且不误撤销正常会话，超过配置化宽限窗口的旧令牌重放才撤销会话族。
6. 刷新会话默认 30 分钟无活动失效，最长有效期由环境变量配置。
7. 密码、角色、站点范围或账号状态变更时增加 `token_version`；认证过滤器必须对照当前账号状态和版本，或使用可立即失效的短时缓存，确保旧访问令牌和刷新令牌确实失效。
8. JWT 签名密钥、Cookie 安全开关和初始管理员凭据只从环境变量读取，不写入仓库。
9. 业务认证只接受 Bearer Token。刷新 Cookie 端点必须校验受信 `Origin`，并记录禁用 CSRF 的边界；如果后续让 Cookie 直接认证业务请求，必须启用 CSRF Token。

### 28-T02：新增用户与会话数据模型

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 依赖 | 28-T01 |
| 迁移 | `V34__authentication_and_rbac.sql` |
| 核心表 | `system_user`、`system_user_station_scope`、`auth_refresh_token` |
| 后端实现 | 领域模型、Repository 接口、内存实现、MyBatis Entity/Mapper/Repository |

数据约束：

1. 用户名唯一且规范化比较；角色只能是四个正式编码；账号支持 `must_change_password` 状态。
2. `CASHIER`、`STORE_MANAGER` 至少绑定一个站点；`SYS_ADMIN` 可全局访问。
3. 刷新令牌只保存哈希、会话族、到期时间、最后使用时间、撤销时间和必要的设备摘要。
4. 不在 SQL 中写默认明文密码或固定可用哈希。首次管理员由环境变量引导初始化，初始化后不得重复覆盖。
5. 默认内存 profile 提供与数据库 profile 相同的接口，测试通过夹具创建用户，不增加匿名绕过开关。
6. 数据库 profile 在没有可用系统管理员且未提供初始化凭据时应快速失败；开发和测试账号必须由显式环境变量或测试夹具提供，不使用通用默认密码。

### 28-T03：实现认证与账号管理服务

| 接口 | 行为 | 访问要求 |
|------|------|----------|
| `POST /api/auth/login` | 校验账号、密码、状态和锁定信息，返回访问令牌与用户信息 | 匿名 |
| `POST /api/auth/refresh` | 校验并轮换刷新令牌，返回新访问令牌 | 刷新 Cookie |
| `POST /api/auth/logout` | 撤销刷新会话并清除 Cookie；无会话时幂等成功 | 匿名，但校验刷新 Cookie 与 Origin |
| `GET /api/auth/me` | 返回用户、角色、权限代码和站点范围 | 已登录 |
| `POST /api/auth/change-password` | 修改本人密码、清除强制改密状态并撤销其他会话 | 正常令牌或 `PASSWORD_CHANGE_ONLY` 受限令牌 |
| `GET /api/users` | 查询授权范围内账号 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |
| `POST /api/users` | 创建账号并绑定站点 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |
| `PUT /api/users/{userId}` | 修改姓名、角色和站点范围 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |
| `POST /api/users/{userId}/password-reset` | 重置密码并失效旧会话 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |
| `POST /api/users/{userId}/disable` | 停用账号并失效旧会话 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |
| `POST /api/users/{userId}/unlock` | 解锁达到失败阈值的账号 | `USER_MANAGE_STATION` 或 `USER_MANAGE_GLOBAL` |

账号管理必须防止区域运营创建或修改 `REGION_ADMIN`、`SYS_ADMIN`，防止用户越过自身站点范围，并禁止停用最后一个可用的系统管理员。管理员重置密码时由请求提交临时密码，响应不得返回密码；目标用户下次登录必须先修改密码。

登录失败响应不得暴露用户名是否存在。失败阈值和锁定时长应配置化，建议默认连续5次失败锁定15分钟；密码最小长度建议默认12位，并禁止使用空白、用户名或内置通用密码。

### 28-T04：为现有接口接入RBAC与站点范围

| 工作 | 要求 |
|------|------|
| 默认保护 | 采用“默认拒绝、显式放行”，避免遗漏新接口 |
| 方法授权 | 对规则、导入、库存、券、积分、运营发券、用户管理等写操作使用方法级授权 |
| 站点校验 | 门店角色只能访问令牌中的站点；不得通过请求体替换站点范围 |
| 查询隔离 | 列表查询在 Repository/Service 层加入站点范围，不允许先查全量再由前端过滤 |
| 敏感信息 | 手机号等字段默认返回脱敏值；完整值需要独立权限并记录访问审计 |
| 错误语义 | 缺少身份返回 401，身份有效但越权返回 403，目标不存在返回 404 |

至少审计所有现有 Controller 路径并输出一份“接口-权限-站点范围”表。未列入权限表的新增端点不得默认公开。

### 28-T05：将关键操作人改为服务端可信身份并强化审计

新增统一的 `CurrentOperatorProvider` 或等价抽象，由 Spring Security Principal 生成 `userId`、显示名、角色和站点范围；单元测试通过可注入的测试实现提供身份。

本轮必须覆盖以下操作：

| 业务操作 | 当前风险 | 改造结果 |
|----------|----------|----------|
| 结算确认与交易流水 | 前端硬编码收银员 | 使用登录用户和授权站点 |
| 规则确认、驳回、修订、停用 | 请求体提交操作人工号 | 忽略伪造字段，审计记录 Principal |
| 导入与错误报告导出 | 查询参数可提交操作人工号 | 由服务端记录下载与导入人 |
| 库存预警处置与补货 | 固定或手工操作人 | 记录登录用户 |
| 券发放、积分变动、抽奖奖池 | 客户端可自报操作人 | 使用授权用户并检查业务权限 |
| 运营活动发券 | 表单允许输入操作员 | 业务备注可保留，身份不可覆盖 |

为兼容当前 DTO，`operatorId/operatorName` 可保留一个版本但必须标记废弃并在服务端忽略；同一轮前端应停止发送这些字段。

在28-T02开始前冻结 V34 的完整内容，V34 只创建认证、用户和会话数据，不在执行后改写。审计演进使用独立的 `V35__trusted_audit_context.sql`：继续以现有 `audit_log.operator_id/operator_name` 作为操作人ID和姓名快照，新登录操作将 `operator_id` 写为 `system_user.user_id`；只追加 `operator_role`、`station_code`、`request_id`、`client_ip`、`outcome` 等非同义字段。历史记录和系统任务的新字段允许为空，不伪造回填用户。

审计 API 不提供修改或删除能力；生产数据库角色应限制应用账号更新、删除审计记录。手机号、令牌、密码和请求体中的敏感值不得写入审计详情。

### 28-T06：接入前端登录态与权限界面

| 阶段 | 工作 | 交付要求 |
|------|------|----------|
| T06A | 登录页 | 账号、密码、强制改密、错误状态、锁定提示、提交中状态；不提供演示角色切换 |

| T06B | 用户管理 | 根据 `USER_MANAGE_STATION`/`USER_MANAGE_GLOBAL` 创建、停用和重置账号 |
| T06B | 操作人字段 | 删除前端硬编码和手工覆盖，业务请求不再发送身份字段 |

访问令牌、刷新令牌和密码均不得写入 `localStorage`。页面刷新依赖刷新 Cookie 恢复会话。

## 十、工程约束与风险控制

1. 不修改 V1-V33 历史迁移，只追加 V34 及后续迁移。
2. 不提交真实账号、密码、JWT 密钥、刷新令牌或生产站点授权数据。
3. 认证失败和授权失败不得进入业务 Service，不得产生部分写入。
4. 账号停用、密码重置、角色变更和站点范围变更必须在同一事务内更新用户并撤销会话。
5. 站点隔离必须下沉到服务或仓储查询，不能只依赖 Controller 参数检查。
6. 安全过滤器之外的错误也继续使用统一 `ApiResponse`；日志中不得输出密码、完整令牌或敏感个人信息。
7. 兼容默认内存 profile 和 `dev-db` profile，禁止为了测试方便增加默认匿名管理员。
8. 保留工作区现有未提交成果，不回滚与 DEV-28 无关的文件。
9. 对现有 API 请求体的身份字段采用“保留但忽略并废弃”的短期兼容策略，不允许继续信任。
