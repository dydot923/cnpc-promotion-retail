# 加油站促销智能零售系统架构优化方案

## 一、优化结论

本项目一期必须优先完成“促销智能计算引擎”，并把它作为整个系统的核心底座，而不是先做页面、报表或海报生成。原因很直接：扫码结算、库存预警、补货建议、活动看板、海报卖点生成，最终都依赖同一套促销规则理解能力。如果项目前期没有把结算引擎的数据模型、规则模型、计算流程、解释能力和测试体系做好，后续每新增一个活动都会变成临时判断代码，系统会很快失控。

一期建设重点应调整为：

1. 先建立商品、价格、库存、活动、商品组、券、组合包的标准数据模型；
2. 再建立可扩展的促销规则 DSL 或 JSON 规则模型；
3. 再实现促销计算引擎、互斥叠加策略、最优方案推荐、规则解释；
4. 最后接入前台扫码页、库存预警、补货导出和 AI 海报。

可以把本项目理解为：

```text
促销智能计算引擎是内核
扫码结算是第一业务入口
库存预警是第二业务入口
AI 海报是营销输出入口
数据导入是规则供给入口
```

其中“促销智能计算引擎”必须在项目前期做扎实。

---

## 二、一期优先级重排

### P0：促销智能计算引擎

必须优先完成，作为所有功能的基础。

范围包括：

- 购物车模型；
- 油品消费上下文；
- 会员上下文；
- 商品组模型；
- 组合包模型；
- 促销规则模型；
- 条件匹配器；
- 优惠动作计算器；
- 互斥与叠加处理；
- 最优方案排序；
- 规则解释；
- 规则测试用例。

P0 的成功标准不是“页面能展示优惠”，而是“给定一组订单上下文，系统能稳定、可解释、可测试地输出候选促销方案”。

### P1：扫码结算前台

在 P0 稳定后建设。

范围包括：

- 条码输入；
- 商品识别；
- 购物车；
- 油品消费录入；
- 会员状态录入；
- 候选促销方案展示；
- 方案选择、跳过、返回；
- 结算摘要。

前端不应承载促销判断逻辑，只负责收集上下文、展示结果、提交用户选择。

### P2：数据导入与规则维护后台

范围包括：

- 价格表导入；
- 库存表导入；
- 活动看板导入；
- 商品组维护；
- 组合包维护；
- 规则启停；
- 优先级和互斥组配置；
- 导入异常处理。

活动看板中的自然语言规则不能全部依赖自动解析。系统应支持“半自动导入 + 人工确认 + 模板化规则配置”。

### P3：库存预警与补货导出

范围包括：

- 活动商品与本站库存交集；
- 安全库存阈值；
- 组合包可售套数；
- 预警等级；
- 建议补货量；
- 补货 Excel 导出。

库存预警依赖促销规则库和商品组模型，因此应在 P0 后启动。

### P4：AI 海报生成

范围包括：

- 从促销规则提取卖点；
- 从商品和价格提取展示文案；
- 生成提示词；
- 调用图像模型；
- 预览、换一批、下载。

海报模块不应成为一期核心风险点。它依赖准确的商品价格和促销文案，应在规则引擎稳定后再接入。

## 三、促销智能计算引擎架构

### 3.1 引擎定位

促销智能计算引擎应作为独立领域模块存在，不绑定前端、不绑定 Excel、不绑定具体数据库表。它只接收标准化输入，输出标准化结果。

```text
输入：OrderContext + PromotionRules + ProductSnapshot + InventorySnapshot
输出：PromotionCandidate[]
```

这样做有三个好处：

1. 方便做单元测试；
2. 方便后续接 POS、会员、电子券系统；
3. 方便把促销能力复用到库存预警、海报生成和运营看板。

### 3.2 标准输入模型

#### OrderContext

订单上下文建议包含：

```json
{
  "station": {
    "station_id": "string",
    "station_type": "gas_station",
    "region": "新疆"
  },
  "customer": {
    "is_member": true,
    "member_level": "gold",
    "available_coupons": []
  },
  "fuel": {
    "fuel_type": "gasoline",
    "fuel_grade": "CN98",
    "amount": 230,
    "volume": 30
  },
  "cart": [
    {
      "sku_code": "70536790",
      "barcode": "6970372689919",
      "name": "咔咔酷优特 汽车风窗玻璃清洗液0℃（新疆） 2L",
      "quantity": 2,
      "unit_price": 12,
      "category": "玻璃水"
    }
  ],
  "time": {
    "business_date": "2026-07-09",
    "business_time": "20:30:00"
  }
}
```

#### PromotionRule

促销规则建议使用 JSON 配置，后端用强类型模型校验。

```json
{
  "rule_id": "promo_0099_area",
  "activity_name": "9.9零食好物集",
  "rule_type": "fixed_price",
  "priority": 50,
  "exclusive_group": "direct_discount",
  "stackable": false,
  "conditions": {
    "date_range": null,
    "day_of_month": null,
    "member_required": false,
    "station_types": ["gas_station"],
    "product_scope": {
      "type": "sku_list",
      "sku_codes": ["70424725", "70452735"]
    }
  },
  "benefit": {
    "type": "fixed_price",
    "fixed_price": 9.9,
    "quantity": 1
  },
  "constraints": {
    "exclude_categories": ["香烟", "化肥"],
    "min_gross_margin_rate": 0.08
  }
}
```

### 3.3 引擎内部模块

促销引擎建议拆成 7 个内部模块：

1. ContextNormalizer  
   标准化订单上下文，补全商品品类、价格、库存、站点、时间。

2. RuleFilter  
   初筛有效规则，过滤未启用、日期不符、站点不符、会员不符的规则。

3. ConditionMatcher  
   判断订单是否满足具体规则条件，包括金额、数量、商品组、油品类型、时间段等。

4. BenefitCalculator  
   计算优惠动作，包括折扣、立减、固定价、换购价、买赠、赠券、积分倍率。

5. ConflictResolver  
   处理互斥组、叠加、优先级、毛利底线、库存限制。

6. CandidateRanker  
   对候选方案排序，给出系统推荐方案。

7. ExplanationBuilder  
   生成可给收银员、站长和测试人员看的解释文本。

### 3.4 规则类型优先支持清单

一期不要一口吃完所有规则，建议按以下顺序支持：

1. fixed_price：固定促销价，例如 9.9 元专区；
2. percentage_discount：折扣，例如全场 9 折、夜间 8.8 折；
3. amount_off：满减，例如满 326 减 66；
4. exchange_purchase：加油换购，例如汽油满 180 元 +2 元换购 4 瓶水；
5. gift_item：买赠，例如满 40 元赠自有奶；
6. gift_coupon：赠券，例如汽油满 230 元赠便利店券；
7. bundle_price：组合包价，例如行车包、水饮包；
8. points_multiplier：积分倍率，作为二期扩展。

### 3.5 互斥与叠加策略

必须项目前期明确，不能交给页面临时判断。

建议规则：

- 同一商品同一数量维度只能命中一个直接降价类优惠；
- fixed_price、percentage_discount、amount_off 默认互斥；
- gift_coupon 可配置是否与直接降价叠加；
- exchange_purchase 可配置是否与油品赠券叠加；
- gift_item 必须校验赠品库存；
- bundle_price 对组合包内商品占用数量，避免同一件商品重复参与其他优惠；
- 香烟、化肥默认排除全场便利店折扣，但可参与专门香烟规则；
- 毛利率低于活动底线时，候选方案应标记为 blocked，不进入可选列表。

### 3.6 规则解释输出

每个候选方案应输出：

```json
{
  "candidate_id": "cand_001",
  "title": "逢9全场9折",
  "status": "available",
  "original_amount": 100,
  "payable_amount": 90,
  "discount_amount": 10,
  "gifts": [],
  "coupons": [],
  "reason": "当前日期为每月9日，站点类型为加油站，商品不属于香烟或化肥，满足全场9折条件。",
  "blocked_reasons": []
}
```

不可用方案也应输出原因：

```json
{
  "title": "汽油满180元换购4瓶小水",
  "status": "blocked",
  "blocked_reasons": ["当前汽油消费金额为150元，未达到180元门槛"]
}
```

这会显著降低收银员解释成本，也方便测试。

## 四、技术选型建议

### 4.1 推荐技术栈

#### 前端

- React 18
- TypeScript
- Vite
- Ant Design 或 Arco Design
- Zustand 或 Redux Toolkit
- TanStack Query

选择理由：

- 适合快速构建后台和收银操作界面；
- TypeScript 能降低促销方案字段使用错误；
- Ant Design/Arco 适合表格、弹窗、表单、导入导出、管理后台。

#### 后端

推荐优先选：

- Python 3.11+
- FastAPI
- Pydantic v2
- SQLAlchemy 2.x
- Alembic
- PostgreSQL
- Redis，可选

选择理由：

- Python 对 Excel 导入、规则处理、AI 接口调用友好；
- FastAPI + Pydantic 适合定义强类型请求响应；
- PostgreSQL 适合存储结构化数据和 JSONB 规则；
- 后续 AI 海报服务也更容易集成。

如果企业 Java 技术栈更强，也可选：

- Java 21
- Spring Boot 3
- PostgreSQL
- Drools 或自研规则引擎

但本项目规则高度业务定制，早期不建议直接上重型 Drools，除非团队已有成熟经验。

#### 数据库

MVP 可选：

- SQLite，用于本地演示；

正式试点建议：

- PostgreSQL；

原因：

- 支持事务；
- 支持 JSONB；
- 支持复杂查询；
- 后续多站点扩展更稳。

#### Excel 导入导出

- Python openpyxl；
- 后续可引入 pandas，但核心导入逻辑不依赖 pandas。

#### 测试

- 后端：pytest；
- 前端：Vitest + React Testing Library；
- 端到端：Playwright；
- 规则测试：JSON fixtures + pytest snapshot。

#### AI 海报

- 通过后端封装图像生成 API；
- 不让前端直接持有密钥；
- 海报价格、活动条件尽量用结构化模板叠加或二次审核。

### 4.2 架构风格

推荐采用“模块化单体 + 清晰领域边界”，不要一开始做微服务。

```text
apps/web              前端
apps/api              后端 API
packages/rules        促销规则引擎
packages/importer     Excel 导入解析
packages/shared       共享类型或接口定义
```

后端内部可按领域拆分：

```text
modules/products
modules/prices
modules/inventory
modules/promotions
modules/checkout
modules/replenishment
modules/posters
modules/audit
```

促销规则引擎应能被 checkout、replenishment、poster 三个模块复用。

## 五、核心约束

### 5.1 业务约束

1. 促销计算必须可解释  
   每个可用或不可用方案都要说明原因。

2. 促销规则必须可测试  
   每条关键规则都要有输入订单和预期输出。

3. 前端不得写促销判断逻辑  
   前端只展示后端引擎输出，避免多端逻辑不一致。

4. 活动导入不得覆盖人工确认结果  
   Excel 导入是来源，不是最终规则真相。人工修正后的结构化规则应有版本管理。

5. 原价结算必须始终可用  
   即使促销引擎异常，不能阻断门店收银。

6. 库存不是活动可执行的唯一条件  
   活动命中还必须满足日期、站点、会员、商品、油品金额、互斥规则。

7. 站点有货才推荐前台执行  
   活动商品池中本站无库存的商品，不应在收银前台作为可执行促销重点推荐。

8. 敏感品类必须配置排除  
   香烟、化肥等默认排除全场折扣，除非存在专门规则。

### 5.2 技术约束

1. 规则引擎独立于 Web 框架  
   不允许把促销计算散落在 Controller、API Route 或 React 组件中。

2. 规则输入输出必须强类型  
   使用 Pydantic 或 TypeScript schema 校验。

3. 金额计算必须使用 Decimal  
   后端不得用浮点数直接计算金额。

4. 所有规则版本可追溯  
   订单结果要记录使用的规则版本。

5. Excel 导入必须有异常报告  
   缺失商品编码、价格缺失、库存缺失、规则不可解析都要输出。

6. 关键接口必须有契约测试  
   尤其是 `/checkout/calculate`。

7. AI 海报不得作为价格真相来源  
   价格和活动文案由系统结构化数据提供，AI 只负责视觉生成。

8. 不提前微服务化  
   先做模块化单体，等多站点规模化后再拆服务。

### 5.3 项目管理约束

1. 一期验收以促销计算准确性为第一指标；
2. 每次新增促销类型必须补规则测试；
3. 每周固定评审规则样例和异常样例；
4. 需求变更先进入规则模型评估，再进入页面开发；
5. 页面演示不能替代引擎测试；
6. 任何临时促销判断必须回收进规则引擎。

## 六、建议接口

### 6.1 促销计算接口

```http
POST /api/checkout/calculate
```

输入：

```json
{
  "station": {},
  "customer": {},
  "fuel": {},
  "cart": [],
  "time": {}
}
```

输出：

```json
{
  "cart_summary": {
    "original_amount": "100.00"
  },
  "candidates": [],
  "recommended_candidate_id": "cand_001",
  "unavailable_promotions": [],
  "warnings": []
}
```

### 6.2 确认促销方案接口

```http
POST /api/checkout/confirm
```

记录用户选择的促销方案，返回最终结算摘要。

### 6.3 规则测试接口

```http
POST /api/promotions/rules/test
```

用于后台运营人员输入订单样例，验证某条规则是否按预期触发。

### 6.4 低库存预警接口

```http
GET /api/replenishment/alerts
```

返回活动商品低库存、缺货、组合包不可组装等信息。

## 七、四个子 Agent 的协作方式

建议将项目拆成 4 个子 agent：

1. Planner  
   负责需求拆解、规则建模、迭代计划、验收口径。

2. Frontend  
   负责收银界面、活动后台、库存预警、海报页面。

3. Backend  
   负责数据模型、API、Excel 导入、促销规则引擎、测试。

4. Reviewer  
   负责架构审查、规则准确性审查、测试覆盖、风险控制。

协作原则：

- Planner 先定义规则样例和验收条件；
- Backend 先完成引擎和接口；
- Frontend 基于接口契约做页面；
- Reviewer 对规则、金额、互斥、库存、异常路径进行审查；
- 所有 agent 都必须承认促销计算引擎是一期开工优先级最高的模块。

## 九、最终建议

项目一期不要被“页面看起来完整”牵着走。真正决定系统成败的是促销智能计算引擎。只要引擎足够稳定，前台结算、库存预警、补货、海报、活动看板都可以围绕它自然生长；如果引擎前期没做好，后面所有功能都会变成不断补丁化的条件判断。

因此建议项目启动后前两到三周集中完成规则模型、真实样例、促销计算引擎和测试体系，再进入完整页面和 AI 海报模块开发。
